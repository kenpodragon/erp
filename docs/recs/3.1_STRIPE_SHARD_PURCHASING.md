## 1. Overview & Scope

### 1.1 Purpose
Section 3.1 establishes the real-money payment pipeline connecting Stripe to the game's premium currency (Elysium Shards). This includes:
- Stripe Checkout Sessions for one-time shard package purchases
- Webhook-driven payment lifecycle (confirmation, failure, refund, dispute)
- Shard crediting with full idempotency and audit trail
- Player-facing transaction history
- Administrative refund and dispute handling

### 1.2 Scope Boundaries
- **In Scope:** Stripe Checkout, webhook handler, shard packages, crediting flow, idempotency, refund/chargeback handling, Stripe Customer linking, receipt storage, transaction history UI, reconciliation polling.
- **Out of Scope:** Subscriptions (3.2), shop/spending (3.3), donations (3.4), marketplace (3.5), admin dashboard (3.6). These all build on the 3.1 foundation.
- **Dependencies:** Firebase Auth (1.0), `shard_balance` on `player_meta_progression` (2.7.0/046), `shard_transactions` table (2.7.0/046).

### 1.3 Existing Foundation
| Component | Source | Description |
|:---|:---|:---|
| `shard_balance` | `player_meta_progression` (046) | Integer balance field, currently 0 for all players |
| `shard_transactions` | Table (046) | Audit trail with `player_id`, `amount`, `balance_after`, `source_type`, `source_id`, `description` |

## 2. Shard Package Definitions

### 2.1 Package Tiers
Six fixed tiers with volume-based bonus scaling (~100 shards per $1 base rate):

| Tier | Tier Key | Price (USD) | Base Shards | Bonus % | Total Shards | Shards/$ |
|:---|:---|:---|:---|:---|:---|:---|
| Starter | `starter` | $0.99 | 100 | 0% | 100 | ~101 |
| Small | `small` | $4.99 | 500 | 5% | 525 | ~105 |
| Medium | `medium` | $9.99 | 1,000 | 10% | 1,100 | ~110 |
| Large | `large` | $24.99 | 2,500 | 12% | 2,800 | ~112 |
| Premium | `premium` | $49.99 | 5,000 | 20% | 6,000 | ~120 |
| Ultimate | `ultimate` | $99.99 | 10,000 | 30% | 13,000 | ~130 |

### 2.2 Purchase Rules
- **No spending cap.** Players may purchase any package any number of times with no daily or weekly limit.
- **Repeat purchases allowed.** The same tier can be bought multiple times in succession.
- **Limited-quantity packages:** Some packages may have an optional `max_purchases_per_player` limit (e.g., a one-time "Welcome Pack"). When set, the backend enforces the cap and the UI shows remaining quantity. Most packages have no limit (NULL = unlimited).

### 2.3 First-Purchase Bonus
- **2x shards** on the buyer's very first package purchase (any tier).
- Tracked via `first_purchase_claimed` boolean on the player record.
- Applied after the volume bonus (e.g., first-time Ultimate = 13,000 × 2 = 26,000 shards).
- One-time only. Subsequent purchases receive only the standard volume bonus.
- **Permanently consumed.** If the first purchase is later refunded, the bonus is NOT reset. The player does not get a second chance at the 2x bonus.

### 2.4 Admin Configurability
- All package definitions (price, base shards, bonus %, active status, max purchases) are stored in the database and manageable via the Admin panel (3.6).
- Packages can be deactivated without deletion (soft-disable).
- Price changes do NOT affect already-completed transactions.

## 3. Stripe Integration

### 3.1 Stripe Checkout Session Flow
1. **Player selects a package** in the Shard Shop UI.
2. **Frontend calls** `POST /api/payments/checkout` with `package_id`.
3. **Backend creates** a Stripe Checkout Session in `payment` mode:
   - `line_items`: Single item matching the selected package (name, price, quantity=1).
   - `metadata`: `player_id`, `package_id`, `idempotency_key` (UUID generated per request).
   - `success_url`: Redirect back to game with `?session_id={CHECKOUT_SESSION_ID}`.
   - `cancel_url`: Redirect back to Shard Shop.
   - `customer`: Stripe Customer ID (created/linked on first purchase — see §3.2).
   - `expires_at`: 30 minutes from creation (override Stripe's 24-hour default).
   - **Payment methods:** All Stripe-supported methods enabled (card, Apple Pay, Google Pay, Link, etc.).
4. **Backend returns** the Checkout Session URL.
5. **Frontend redirects** to Stripe-hosted payment page.
6. **On completion**, Stripe fires `checkout.session.completed` webhook.
7. **On success redirect**, frontend polls `/api/payments/status/{session_id}` until confirmed.

### 3.2 Stripe Customer Linking
- On a player's first purchase attempt, create a Stripe Customer object with:
  - `email`: From Firebase Auth profile.
  - `metadata`: `player_id`, `firebase_uid`.
- Store the `stripe_customer_id` on the player record.
- All subsequent Checkout Sessions attach to this Customer for receipt/history grouping.
- **Email receipts:** Stripe automatic email receipts are enabled so players receive a confirmation email on every successful purchase.

### 3.3 Webhook Handler
A single webhook endpoint `POST /api/webhooks/stripe` handles all Stripe events:

| Event | Action |
|:---|:---|
| `checkout.session.completed` | Validate → credit shards → log transaction → mark order fulfilled |
| `checkout.session.expired` | Mark order as expired (no action on shards) |
| `charge.refunded` | Debit shards → log transaction with `source_type = 'refund'` |
| `charge.dispute.created` | Flag account → debit shards → log anomaly |
| `charge.dispute.closed` | If won: reverse debit. If lost: keep debit, escalate flag. |

**Webhook Security:**
- Verify Stripe signature using `STRIPE_WEBHOOK_SECRET` on every request.
- Reject requests with invalid or missing signatures (HTTP 400).
- Return HTTP 200 immediately after queuing processing (async handler).

### 3.4 Idempotency
- Each Checkout Session maps to exactly one `payment_order` record (see Schema doc).
- The `stripe_checkout_session_id` is the idempotency key for crediting.
- Before crediting shards, check if a `shard_transactions` record already exists for this `source_id` (checkout session). If yes, skip (no double-credit).
- Stripe webhook retries are safe because of this check.

## 4. Shard Crediting & Balance Management

### 4.1 Credit Flow (Purchase)
1. Webhook `checkout.session.completed` fires.
2. Look up `payment_orders` by `stripe_checkout_session_id`.
3. If `status` is already `completed` → return 200 (idempotent).
4. Calculate total shards: `package.total_shards` × (2 if first purchase else 1).
5. **Atomic transaction:**
   a. `UPDATE player_meta_progression SET shard_balance = shard_balance + :amount`
   b. `INSERT INTO shard_transactions` with `source_type = 'purchase'`, `source_id = payment_order.id`
   c. `UPDATE payment_orders SET status = 'completed', shards_credited = :amount, completed_at = NOW()`
   d. If first purchase: `UPDATE players SET first_purchase_claimed = TRUE`
6. Commit.

### 4.2 Debit Flow (Refund)
1. Webhook `charge.refunded` fires.
2. Look up `payment_orders` by `stripe_payment_intent_id`.
3. Calculate shards to debit using **proportional formula:**
   - `shards_to_debit = floor(shards_credited × (refund_amount_cents / price_cents))`
   - Example: Player bought Medium (1,100 shards for $9.99). $5.00 partial refund → `floor(1100 × 500/999) = 550` shards debited.
   - Full refund → debit the full `shards_credited` amount.
4. **Atomic transaction:**
   a. `UPDATE player_meta_progression SET shard_balance = shard_balance - :amount`
   b. `INSERT INTO shard_transactions` with `source_type = 'refund'`, negative `amount`
   c. `UPDATE payment_orders SET shards_refunded = shards_refunded + :amount, refunded_at = NOW()`
   d. If fully refunded: `UPDATE payment_orders SET status = 'refunded'`
5. **Balance can go negative** if shards were already spent — this is intentional. Negative balance prevents further shard spending until resolved.
6. **First-purchase bonus is permanently consumed.** Refunding the first purchase does NOT reset `first_purchase_claimed`. The 2x bonus cannot be reclaimed.

### 4.3 Debit Flow (Dispute/Chargeback)
1. Webhook `charge.dispute.created` fires.
2. Same debit logic as refund.
3. Additionally: set `account_flag = 'dispute'` on the player record.
4. Log to `activity_events` with type `payment_dispute`.
5. If dispute is later resolved in the game's favor (`charge.dispute.closed` with `status = 'won'`):
   - Reverse the debit (re-credit shards).
   - Clear the account flag.

## 5. Reconciliation & Polling

### 5.1 Receipt Reconciliation (Cron/Scheduled)
A periodic background job (daily) that:
1. Fetches all Stripe charges for ERP's Customer objects from the last 48 hours.
2. Cross-references against `payment_orders` in the database.
3. Identifies any missing credits (e.g., webhook was lost) and retroactively credits shards.
4. Logs reconciliation results to `activity_events`.

### 5.2 Refund/Dispute Polling (Cron/Scheduled)
A periodic background job (every 6 hours) that:
1. Fetches all Stripe refunds and disputes from the last 48 hours.
2. Cross-references against `payment_orders`.
3. Identifies any unprocessed refunds/disputes and applies the debit flow.
4. Flags accounts with unresolved disputes.

### 5.3 Balance Integrity Check
An on-demand admin tool (and optional daily cron) that:
1. For each player with `shard_balance > 0` OR any `shard_transactions`:
2. Recalculates expected balance by summing all `shard_transactions.amount`.
3. Compares to `shard_balance` on `player_meta_progression`.
4. Logs discrepancies to `activity_events` with type `shard_balance_mismatch`.

## 6. Player-Facing UI

### 6.1 Shard Shop Page
- **Same page as the Overworld Shop (3.3).** The Shop is a single unified page with tabs/sections: "Buy Shards" (this section) and "Spend Shards" (cosmetics/boosters, built in 3.3). For 3.1, the "Buy Shards" tab is the only active section.
- Displays all active shard packages in a card grid:
  - Package name, shard count, bonus %, price.
  - "Best Value" badge on the tier with the highest shards/$ ratio.
  - First-purchase 2x banner if player has not yet purchased.
  - For limited-quantity packages: "X remaining" indicator.
- Current shard balance displayed prominently at the top.
- **Age disclaimer:** "You must be 18 or older to make purchases." displayed near the purchase area.
- **Legal footer:** Link to Terms of Service §6 (Virtual Currency & Purchases). Brief disclaimer: "All purchases are final. Elysium Shards are digital goods with no real-world monetary value."
- Clicking a package opens a confirmation modal:
  - Package details, final shard amount (including first-purchase bonus if applicable).
  - "Proceed to Payment" button → redirects to Stripe Checkout.
- Post-payment success: animated shard-gained overlay + balance update.

### 6.2 Shard Balance in Top Bar
- The shard balance is **permanently visible** in the Hub top bar alongside Gold and Essence. An existing placeholder already exists in `TopBar.tsx` (💎 icon with hardcoded "10"). Replace the hardcoded value with the player's actual `shard_balance` from the API.
- Clicking the shard balance navigates to the Shop page.

### 6.3 Transaction History
- Accessible from Player Profile or Shard Shop.
- Paginated list of all `shard_transactions` for the current player.
- Columns: Date, Type (Purchase/Refund/Reward/Spend), Description, Amount (+/-), Balance After.
- Filter by type and date range.

#### 6.3.1 Refund Request Flow
- **Eligibility:** A "Request Refund" link appears on purchase transaction rows only if:
  - The purchase was made within the last **14 days**, AND
  - The credited shards have **not been fully spent** (i.e., the player's balance still covers at least some of the credited amount, or the order has `shards_credited - shards_refunded > 0`).
- **If ineligible** (older than 14 days or shards fully spent): the row shows a "Contact Support" link instead, which navigates to the Support tab for manual review.
- **Refund Confirmation Modal** presents two options:
  1. **Partial Refund:** Player enters a custom dollar amount (up to the original price minus any prior refunds). Proportional shards are debited. Balance stays positive or goes to zero.
  2. **Full Refund:** Refunds the entire remaining amount. Modal shows a warning: *"A full refund will debit [X] shards. If you've spent shards from this purchase, your balance will go negative to [Y]. You won't be able to use the Shop until your balance is positive again (via new purchases or earning shards)."*
- **On confirm:** Creates a support ticket (existing support system from 1.0) tagged as `refund_request` with the `payment_order_id` and requested refund type/amount. Admins process refund requests via the Support Dashboard or Admin Finance panel (3.6).
- **Note:** Stripe also allows buyers to request refunds on their end. Admins can initiate refunds from the admin panel when handling support tickets. All refund paths ultimately flow through the same Stripe refund → webhook → debit pipeline.

### 6.4 Payment Status Indicator
- While a Checkout Session is pending, show a "Payment Processing..." indicator.
- Frontend polls `/api/payments/status/{session_id}` every 3 seconds (max 60 seconds).
- On confirmation: success animation + balance refresh.
- On timeout: "Payment is still processing. Your shards will appear shortly." message.

## 7. Error Handling & Edge Cases

### 7.1 Failed Payments
- Stripe handles payment failures on its Checkout page (retry, alternate card).
- If the session expires without payment: `checkout.session.expired` → mark order as `expired`.
- No shards are credited for failed/expired sessions.

### 7.2 Network Failures
- Webhook retries (Stripe retries for up to 3 days) combined with reconciliation polling (§5.1) ensure no lost credits.
- Frontend success redirect + polling handles cases where the redirect fires before the webhook.

### 7.3 Account Edge Cases
- **Banned/suspended player purchases:** Webhook handler checks player status before crediting. If banned, credit shards but flag for admin review (player paid real money).
- **Concurrent purchases:** Each Checkout Session has its own `payment_order`. Atomic balance updates with row-level locking prevent race conditions.
- **Negative balance after refund:** Player cannot spend shards while balance is negative. They must purchase more shards to bring balance positive, or contact support. However, **achievement shard rewards still credit normally** and offset the negative balance (e.g., -50 + 2 achievement shards = -48).
- **Purchases during active dispute:** If `account_flag = 'dispute'`, the checkout endpoint returns an error. No new purchases can be made until the dispute is resolved to ensure account integrity.
- **Limited-quantity packages:** If `max_purchases_per_player` is set, checkout validates the player hasn't exceeded the cap before creating a Stripe session.

## 8. Security Requirements

### 8.1 Webhook Verification
- All webhook requests MUST be verified using Stripe's signature verification (`stripe.Webhook.construct_event`).
- The `STRIPE_WEBHOOK_SECRET` MUST be stored in environment variables / Google Secret Manager. Never hardcoded.

### 8.2 API Authentication
- All `/api/payments/*` endpoints require Firebase JWT authentication.
- Player can only create Checkout Sessions for themselves (no purchasing on behalf of others).
- Transaction history is scoped to the authenticated player only.

### 8.3 Logging & Audit
- Every shard balance change MUST have a corresponding `shard_transactions` record.
- All webhook events are logged to `stripe_webhook_events` (see Schema doc) for debugging.
- Sensitive data (full card numbers, CVV) is never stored — Stripe handles all PCI compliance.

### 8.4 Rate Limiting
- `POST /api/payments/checkout`: Max 5 requests per player per minute.
- `POST /api/webhooks/stripe`: No rate limit (Stripe controls delivery), but signature verification prevents abuse.

### 8.5 Age & Legal Requirements
- **Minimum age:** 18+ to purchase. Stripe handles card-holder age verification. The Shop UI displays an "18+ to purchase" notice.
- **Terms of Service update:** The existing ToS §6 ("Virtual Currency & Purchases") in `TermsPage.tsx` must be expanded to include:
  - All sales are final. Elysium Shards are digital goods.
  - Shards have no real-world monetary value and cannot be exchanged for cash.
  - Shards should be considered donations/contributions to the game's development.
  - The service may be interrupted, shut down, or experience data loss. No warranty or guarantee of availability.
  - If the service shuts down, all virtual currency and goods are forfeited with no compensation.
  - Refund requests are handled on a case-by-case basis at the operator's discretion.
- **ToS last-updated date** must be bumped, triggering the existing re-acceptance flow for returning players.

| 10 | Limited-quantity packages | Optional `max_purchases_per_player` per package. Most packages unlimited (NULL). |
