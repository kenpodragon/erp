## 1. Overview

### 1.1 Purpose
The Asset Registry is a centralized database-driven system for managing **all visual assets** in ERP. Every sprite, icon, background, portrait, badge, and visual effect is stored as a **procedural definition in JSONB metadata** — following the same pattern established by the Web Audio system (`atmospheres` + `audio_configs`), where lightweight JSON definitions in the DB replace large binary files.

**No filesystem PNGs.** All existing PNG assets (`frontend/public/assets/`) will be converted to inline procedural definitions and the filesystem copies retired. Going forward, C_ generators write directly to the DB, and the frontend renders everything from metadata definitions.

### 1.2 Why Procedural-Only?
- **Single source of truth:** The DB is the authority for all visuals. No file sync issues.
- **C_ generator pipeline:** Generators INSERT/UPDATE rows directly — no manifest files, no file I/O.
- **Instant preview:** Admin can see exactly what will render by previewing the metadata definition.
- **Parameterized variation:** Rarity tints, level scaling, class colors, and seasonal variants are metadata transforms — not separate files.
- **Platform reusability:** Loading a new book series means populating DB rows, not shipping asset directories.

### 1.3 Analogy to Audio System
| Audio System (2.5) | Asset Registry (5.7) |
|---------------------|----------------------|
| `atmospheres` table → music synthesis definitions | `asset_registry` table → visual rendering definitions |
| `audio_configs` table → SFX preset definitions | Same table covers all visual categories |
| `MusicManager.tsx` → Web Audio API renderer | `AssetRenderer.tsx` → Canvas/PixiJS renderer |
| `SFXEngine.tsx` → SFX playback | Per-category renderers (entity, background, icon, etc.) |
| JSON `music_definitions` column | JSON `render_definition` column |

### 1.4 Scope
- **In Scope:** Asset registry table, admin CRUD page, canvas preview, orphan detection (both directions), bulk import, category management, migration of all 21 existing filesystem assets to procedural definitions, retirement of `GAME_ASSETS_GUIDE.md` filesystem patterns.
- **Out of Scope:** C_ generator implementations (they consume the registry, built later). Actual art direction / visual design of specific assets. Animation system (future enhancement).
- **Dependencies:** None — this is the foundation. All subsequent 5.x sections and C_ generators depend on this.

## 2. Asset Categories

Every asset in the registry belongs to exactly one category. The category determines which **renderer** the frontend uses and what **metadata fields** are expected in the `render_definition`.

### 2.1 Complete Category Taxonomy

| # | Category Key | Description | Consumers | Est. Count |
|---|-------------|-------------|-----------|------------|
| 1 | `entity_sprite` | Enemy, boss, and NPC combat sprites | CombatStage, BossStage, BottomAnimatedBanner, Discovery | 200+ |
| 2 | `class_sprite` | Player character class base visuals (body, layers) | BottomAnimatedBanner, CharacterCreator, ProfileDashboard | 4 |
| 3 | `background` | Chapter parallax layers (far, mid, near) | CombatStage, BottomAnimatedBanner | 400+ (138 chapters × 2-3) |
| 4 | `item_icon` | Equipment / dream item icons | Inventory, Marketplace, shop | 100+ |
| 5 | `artifact_icon` | Curated + generated artifact icons | RelicGallery, ArtifactEditor | 50+ |
| 6 | `achievement_icon` | Achievement badge icons (locked/unlocked) | AchievementMatrix, AchievementEditor | 90+ |
| 7 | `skill_icon` | Skill and skill-action icons | SkillsHotbar, Idle Training | 40+ |
| 8 | `avatar` | Player profile pictures | ProfileDashboard, Leaderboard, Chat | 8+ |
| 9 | `skin` | Character cosmetic skin definitions | BottomAnimatedBanner, CombatStage | 6+ |
| 10 | `badge` | Leaderboard cosmetic frame overlays | HallOfEchoes | 4+ |
| 11 | `flair` | Chat name border/glow effects | Chat messages | 5+ |
| 12 | `spell_effect` | VFX / particle effect definitions | CombatStage, BossStage | 20+ |
| 13 | `ui_icon` | Misc UI elements (shop icons, title icons, booster icons) | Various UI | 30+ |

| 15 | `portrait` | NPC/character lore portraits | Future: Discovery codex, story beats | 20+ |

### 2.2 Category–Renderer Mapping
Each category maps to a specific rendering strategy on the frontend:

| Category | Renderer | Technology |
|----------|----------|------------|
| `entity_sprite` | `EntityRenderer` | PixiJS Graphics — shape composition (circles, rects, polygons), color fills, outlines, features (eyes, horns, aura) |
| `class_sprite` | `ClassRenderer` | PixiJS Graphics — layered body parts (paper-doll), class color tints |
| `background` | `BackgroundRenderer` | Canvas 2D — gradient layers, procedural terrain, parallax-ready tiles |
| `item_icon` | `IconRenderer` | Canvas 2D — shape + border + inner symbol + rarity glow |
| `artifact_icon` | `IconRenderer` | Same as item_icon with artifact-specific shapes |
| `achievement_icon` | `IconRenderer` | Same with locked/unlocked state variants |
| `skill_icon` | `IconRenderer` | Same with cooldown overlay support |
| `avatar` | `AvatarRenderer` | Canvas 2D — face composition (shape, features, colors, accessories) |
| `skin` | `SkinRenderer` | PixiJS — color palette overrides + feature additions on class_sprite base |
| `badge` | `BadgeRenderer` | Canvas 2D — decorative border frame overlay |
| `flair` | `FlairRenderer` | Canvas 2D / CSS — border glow, name decoration effect |
| `spell_effect` | `VFXRenderer` | PixiJS particles — emitter config, colors, timing |
| `ui_icon` | `IconRenderer` | Canvas 2D — generic icon rendering |
| `narrative_image` | `TextImageRenderer` | Canvas 2D — styled text to image (copy-protected) |
| `portrait` | `PortraitRenderer` | Canvas 2D — character face/bust composition |

## 3. Functional Requirements

### 3.1 Asset Registry Table (Backend)
- [x] **R1.** Single `asset_registry` table with `asset_key` (unique), `category`, `display_name`, `render_definition` (JSONB), `tags` (JSONB array), `created_at`, `updated_at`.
- [x] **R2.** `asset_key` follows existing naming convention: `{category_prefix}_{descriptive_name}` (e.g., `enemy_sludge_stalker`, `bg_ch1_far`, `icon_void_shard`, `avatar_pallid_mask`).
- [x] **R3.** `render_definition` is the core payload — contains all data needed to procedurally render the asset. Structure varies by category (see Design doc §3).
- [x] **R4.** `tags` supports freeform labels for filtering/search (e.g., `["book_1", "chapter_3", "void", "boss"]`).
- [x] **R5.** No foreign key constraints from existing `sprite_key` / `icon_sprite_key` columns — loose lookup by key (orphan detection handles integrity).
- [x] **R6.** `source` field tracks origin: `"seed"` (migration), `"admin"` (manual), `"generator"` (C_ pipeline), `"migrated"` (converted from filesystem PNG).

### 3.2 Backend CRUD API
- [x] **R7.** Standard REST endpoints under `/api/admin/assets/`:
  - `GET /` — List all assets (paginated, filterable by category, tags, search term)
  - `GET /{asset_key}` — Get single asset with full render_definition
  - `POST /` — Create new asset
  - `PUT /{asset_key}` — Update asset (full replace of render_definition)
  - `DELETE /{asset_key}` — Delete asset (with orphan warning if referenced)
- [x] **R8.** Orphan detection endpoints:
  - `GET /orphans/missing` — asset_keys referenced in game tables but not in registry
  - `GET /orphans/unused` — registry entries not referenced by any game table
- [x] **R9.** Bulk import endpoint: `POST /bulk` — accepts array of asset definitions, upserts by `asset_key`.
- [x] **R10.** Batch preload endpoint: `GET /batch?keys=a,b,c` — returns multiple asset definitions in one request (used by frontend scene loading).

### 3.3 Admin Asset Registry Page
- [x] **R11.** Grid/table view of all registered assets with columns: thumbnail preview (canvas-rendered), asset_key, category, display_name, tags, source, updated_at.
- [x] **R12.** **Canvas preview column:** Each row shows a small canvas-rendered thumbnail of the asset's `render_definition`. This is the primary way to see what assets look like — there are no image files.
- [x] **R13.** Category filter tabs (one per category + "All").
- [x] **R14.** Search by asset_key, display_name, or tags.
- [x] **R15.** Create/Edit modal with:
  - Text fields for asset_key, display_name, category, source, tags
  - JSON editor for `render_definition` (syntax-highlighted, validated)
  - **Live canvas preview** that re-renders on every edit to the JSON — admin sees exactly what the asset will look like in-game as they edit the definition
- [x] **R16.** Delete with confirmation (warns if asset_key is referenced in game tables).
- [x] **R17.** Orphan detection panel:
  - "Missing Assets" tab — lists all `sprite_key`/`icon_sprite_key` values found in game tables that have no matching `asset_key` in the registry. Click to pre-populate a create form.
  - "Unused Assets" tab — lists registry entries not referenced anywhere. Bulk delete option.

### 3.4 Bulk Import
- [x] **R18.** Import accepts JSON array (same format as `POST /bulk` body). Designed for C_ generators to call directly.
- [x] **R19.** Upsert behavior: if `asset_key` exists, update `render_definition` and `updated_at`. If new, insert.
- [x] **R20.** Import summary: count of created, updated, skipped (with reasons for skips).
- [x] **R21.** Admin UI: paste JSON or upload `.json` file for manual bulk import.

### 3.5 Existing Asset Migration
- [x] **R22.** All 21 existing filesystem assets converted to procedural `render_definition` entries:
  - 8 avatars (`preset_*.png`) → `avatar` category entries with face-composition definitions
  - 8 backgrounds (`bg_*_far/mid.png`) → `background` category entries with gradient/layer definitions
  - 1 class sprite (`base_vessel.png`) → `class_sprite` category entry
  - 4 enemy sprites (`enemy_*.png`) → `entity_sprite` category entries
- [x] **R23.** All existing `sprite_key`, `icon_sprite_key`, `background_sprite_key` values in the DB get corresponding `asset_registry` rows so orphan detection starts clean.
- [x] **R24.** After migration + verification, filesystem assets in `frontend/public/assets/game/` and `frontend/public/assets/avatars/` are retired (deleted or moved to archive).
- [x] **R25.** `GAME_ASSETS_GUIDE.md` updated to reflect the new DB-driven procedural approach.
- [x] **R26.** 4 legacy music WAVs in `frontend/public/music/` also retired (already replaced by Web Audio synthesis in 2.5).

### 3.6 Frontend Asset Rendering
- [x] **R27.** New `AssetRenderer` utility module that takes an `asset_key` + `render_definition` and returns a rendered canvas/PixiJS element.
- [x] **R28.** Category-specific sub-renderers (see §2.2) that interpret the `render_definition` JSONB for their category.
- [x] **R29.** Caching layer: rendered assets cached in memory (Map keyed by `asset_key` + hash of definition) to avoid re-rendering on every frame.
- [x] **R30.** Fallback rendering: if an asset_key is not found in registry, render a labeled placeholder (colored rectangle with the key name) and log to `dev_content_audit`.
- [x] **R31.** All existing PixiJS procedural rendering in CombatStage, BossStage, and BottomAnimatedBanner refactored to use `AssetRenderer` lookups instead of inline draw calls.

## 5. C_ Generator Integration Points

The asset registry is the **target destination** for all C_ content generators. Each generator writes rows directly to `asset_registry` via SQL INSERT/UPDATE or the bulk API.

| Generator | Target Categories | Output Pattern |
|-----------|------------------|----------------|
| Background Parallax Generator | `background` | One row per chapter per layer (`bg_ch{N}_far`, `bg_ch{N}_mid`) |
| Sprite Generator | `entity_sprite`, `class_sprite`, `portrait` | One row per entity/class |
| Icon Generator | `item_icon`, `artifact_icon`, `achievement_icon`, `skill_icon`, `ui_icon` | One row per item/artifact/achievement/skill |
| Cosmetic Asset Generator | `skin`, `badge`, `flair`, `avatar` | One row per cosmetic |
| PNG Text Generator | `narrative_image` | One row per story beat with text content |
| VFX Generator | `spell_effect` | One row per effect definition |

## 6. Non-Functional Requirements

- [x] **NF1.** Asset registry queries must support pagination (default 50, max 200 per page).
- [x] **NF2.** Canvas preview rendering must complete in <100ms per asset for the admin grid view.
- [x] **NF3.** Frontend asset cache must not exceed 50MB memory (LRU eviction).
- [x] **NF4.** Orphan detection queries must complete in <5s even with 1000+ registry entries.
- [x] **NF5.** Bulk import of 100 assets must complete in <10s.
