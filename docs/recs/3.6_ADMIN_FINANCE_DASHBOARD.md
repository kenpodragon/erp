# REC 3.6: Admin Finance Dashboard & Tools

This document defines the complete requirements for the Admin Finance Dashboard — the unified operational control center for all monetary systems in Elysium Rising, including Stripe transactions, shard management, subscriptions, disputes, shop catalog management, marketplace moderation, and revenue analytics.

**Design:** [3.6_ADMIN_FINANCE_DASHBOARD_DESIGN.md](3.6_ADMIN_FINANCE_DASHBOARD_DESIGN.md) | **Schema:** [3.6_ADMIN_FINANCE_DASHBOARD_SCHEMA.md](3.6_ADMIN_FINANCE_DASHBOARD_SCHEMA.md)
**Parent:** [3.0_ECONOMY.md](3.0_ECONOMY.md) §3.6

---

## 1. Overview & Scope

### 1.1 Purpose
Section 3.6 builds the **Admin Finance Dashboard** — a single-page, tabbed admin interface that consolidates all financial management and operational tooling built across 3.1–3.5. While backend admin endpoints already exist for payments, subscriptions, shop, donations, and marketplace, **no admin UI pages exist for any of these domains.** This phase creates a comprehensive management experience with deeper workflows than the simple CRUD endpoints support.

The dashboard provides:
- **Stripe Transaction Viewer:** Searchable log of all purchases, refunds, disputes, and webhook events.
- **Shard Management:** Manual grant/debit tool for support cases, economy health metrics.
- **Subscription Management:** Active subscriber overview, cancel/extend/gift actions, churn metrics.
- **Refund Workflow:** Search → initiate Stripe refund from admin UI → auto-debit shards → log.
- **Dispute Queue:** Flagged accounts from chargebacks with investigation tools and resolution actions.
- **Shop Catalog Management:** Full item/bundle CRUD UI, featured rotation scheduling, booster configuration, purchase analytics.
- **Marketplace Moderation:** Listing review, price anomaly flagging, trade audit, force-remove/reverse actions.
- **Donation Management:** Donor overview, patron tier status, donation statistics.
- **Revenue Analytics:** Server-calculated daily/weekly/monthly breakdowns, ARPU, top spenders, donation totals.

### 1.2 Scope Boundaries
- **In Scope:** Admin UI for all 3.1–3.5 backend endpoints, new backend endpoints for revenue analytics and shard economy health, manual shard adjustment tool, Stripe refund initiation from admin UI, price anomaly detection (logged to activity_events), deeper shop management workflows (rotation scheduling, analytics, bulk operations).
- **Out of Scope:** Real-time WebSocket updates (manual refresh only), automated dispute responses to Stripe, automated price anomaly blocking (admin review only), mobile admin interface, PDF export (future enhancement).
- **CSV Export:** All paginated list views (transactions, subscriptions, donations, listings, trades, disputes) support a **[Export CSV]** button that exports the current filtered dataset.
- **Dependencies:** All 3.1–3.5 backend endpoints (already implemented), Admin auth infrastructure (1.0), Existing admin page framework (React + admin sidebar), Stripe API access.

### 1.3 Existing Foundation

| Component | Source | Description |
|:---|:---|:---|
| `admin_payments.py` | 3.1 | 4 endpoints: reconcile, poll-refunds, check-balances, webhook-events |
| `admin_subscriptions.py` | 3.2 | 5 endpoints: list, gift, extend, force-cancel, streak-override |
| `admin_shop.py` | 3.3 | 9 endpoints: item CRUD, bundle CRUD, player items, admin refund |
| `admin_donations.py` | 3.4 | 3 endpoints: list, stats, player donations |
| `admin_marketplace.py` | 3.5 | 6 endpoints: listings, force-remove, trades, stats, player detail, reverse-trade |
| `payment_service.py` | 3.1 | `credit_shards()`, `debit_shards()`, `credit_shards_direct()`, `check_balance_integrity()` |
| `Dashboard.tsx` | 1.0 | Player analytics dashboard (DAU, registrations, chapter distribution) — **no finance data** |
| Admin sidebar | 1.0 | Navigation component with page routing |

### 1.4 Refresh Model
- **Manual refresh only.** Data loads on page mount and tab switch.
- Each tab has a **Refresh** button for on-demand reload.
- No auto-polling or WebSocket streaming.
- Navigating away and back to a tab triggers a fresh load.

## 3. Tab 1: Overview (Revenue Dashboard)

### 3.1 Revenue Summary Cards
Top-level KPI cards displaying:

| Card | Metric | Calculation |
|:---|:---|:---|
| **Today's Revenue** | Sum of successful payments today (UTC) | `SUM(payment_orders.price_cents) WHERE status='completed' AND completed_at >= today` |
| **This Week's Revenue** | Sum of successful payments in current week | Same, week boundary |
| **This Month's Revenue** | Sum of successful payments in current month | Same, month boundary |
| **Active Subscribers** | Count of active subscriptions | `COUNT(*) FROM player_subscriptions WHERE status = 'active'` |
| **Shards in Circulation** | Total shard balance across all players | `SUM(shard_balance) FROM players` (via `player_meta_progression`) |
| **Marketplace Volume (7d)** | Total shard volume traded in last 7 days | `SUM(price_shards) FROM marketplace_trades WHERE traded_at >= 7d ago` |

### 3.2 Revenue Chart
A bar chart showing **daily revenue** over the last 30 days, broken down by source:
- **Purchases** (shard packages)
- **Subscriptions** (invoice payments)
- **Donations**

### 3.3 Quick Actions
Buttons for common admin tasks:
- **Run Reconciliation** → calls `POST /api/admin/payments/reconcile`
- **Poll Refunds/Disputes** → calls `POST /api/admin/payments/poll-refunds`
- **Check Balance Integrity** → calls `POST /api/admin/payments/check-balances`
- **View Dispute Queue** → navigates to Tab 8

Each button shows the result (success count, errors) in a toast notification.

## 4. Tab 2: Transactions (Stripe Transaction Viewer)

### 4.1 Transaction Log
A paginated, filterable table of all `payment_orders`:

| Column | Description |
|:---|:---|
| Order ID | `payment_orders.id` |
| Player | Player display name + ID (clickable → PlayerDetail) |
| Type | Derived: "Donation" if `donations.payment_order_id` matches, "Subscription" if linked to subscription invoice, else "Purchase" |
| Amount | Price in dollars (`price_cents / 100`) |
| Shards | `shards_credited` / `shards_refunded` |
| Status | `pending`, `completed`, `refunded`, `disputed`, `expired` |
| Stripe Charge | `stripe_charge_id` (truncated, copyable) |
| Date | `created_at` |

### 4.2 Filters
- **Search:** Player name, player ID, Stripe charge ID, order ID
- **Type:** purchase / subscription / donation (multi-select)
- **Status:** pending / completed / refunded / disputed / expired (multi-select)
- **Date Range:** From – To date pickers
- **Amount Range:** Min – Max dollar amount

### 4.3 Transaction Detail Expandable Row
Clicking a row expands to show:
- Full Stripe charge ID (copyable)
- Package details (name, tier) for purchases
- Subscription plan details for subscription payments
- Donation tier for donations
- Refund history (amounts, dates, shards debited)
- Related webhook events
- **[Initiate Refund]** button (see §4.4)

### 4.4 Admin-Initiated Refund Flow
1. Admin clicks **[Initiate Refund]** on a completed transaction.
2. **Refund modal** shows:
   - Transaction details (amount, shards credited, shards remaining)
   - **Refund type:** Full refund or Partial refund (enter amount in cents)
   - **Reason** text field (required)
   - Warning: `"This will call the Stripe Refund API and auto-debit the proportional shards from the player's balance."`
3. On confirm:
   - Backend calls `stripe.Refund.create()` with the charge ID and amount.
   - On Stripe success: `debit_shards()` for the proportional shard amount.
   - Updates `payment_orders` status and `shards_refunded`.
   - Logs to `activity_events` and audit log.
4. On error: displays Stripe error message (e.g., charge already fully refunded).

### 4.5 Webhook Event Viewer
A secondary table (accessible via sub-tab or toggle) showing raw Stripe webhook events:
- Columns: Event ID, Event Type, Processed (Y/N), Error Message, Timestamp
- Filterable by event type
- Uses existing `GET /api/admin/payments/webhook-events`

## 5. Tab 3: Shard Economy

### 5.1 Economy Health Metrics

| Metric | Description | Source |
|:---|:---|:---|
| **Total Shards in Circulation** | Sum of all player shard balances | `SUM(shard_balance) FROM player_meta_progression` |
| **Total Shards Purchased (All Time)** | Sum of all purchase credits | `SUM(amount) FROM shard_transactions WHERE source_type = 'purchase'` |
| **Total Shards Spent (All Time)** | Sum of all debits (shop, marketplace) | `SUM(ABS(amount)) FROM shard_transactions WHERE amount < 0` |
| **Shards Burned (Marketplace Tax)** | Total tax shards removed from economy | `SUM(tax_shards) FROM marketplace_trades` |
| **Net Shard Flow (30d)** | Credits minus debits over 30 days | Calculated from `shard_transactions` |
| **Spend Rate** | Percentage of purchased shards that have been spent | `spent / purchased × 100` |

### 5.2 Shard Flow Chart
A stacked area chart showing daily shard inflows vs outflows over 30 days:
- **Inflows:** Purchases, achievement rewards, subscription stipends, admin grants
- **Outflows:** Shop purchases, marketplace purchases, marketplace tax (burned), admin debits, refund debits

### 5.3 Manual Shard Adjustment Tool
For support cases, promotions, and corrections:

1. Admin enters **Player ID or searches by name/email**.
2. Player card shows: current shard balance, recent transactions (last 5).
3. Admin selects **Grant** or **Debit**.
4. Admin enters **Amount** (positive integer) and **Reason** (required text).
5. **Confirmation modal** shows:
   - Player name, current balance, new balance after adjustment
   - Reason
   - Warning for debits that would make balance negative: `"This will result in a negative balance of [X]."`
6. On confirm:
   - Calls `credit_shards_direct()` or `debit_shards()` with `source_type = 'admin_grant'` or `'admin_deduct'`.
   - Logged to `shard_transactions`, `activity_events`, and audit log.

This tool is **also accessible from the PlayerDetail page** (embedded widget) for contextual support cases.

### 5.4 Balance Integrity Checker
- Button to run `POST /api/admin/payments/check-balances` for all players or a specific player.
- Results table showing mismatches: Player ID, Expected Balance (from transaction sum), Actual Balance, Difference.
- **[Fix]** button per mismatch that creates an admin adjustment to correct the balance.

### 6.2 Filters
- **Status:** active / canceling / past_due / expired (multi-select)
- **Plan:** monthly / annual (`plan_key`)
- **Search:** Player name, player ID
- **Date Range:** Subscription start date

### 6.3 Subscription Actions
Each row has action buttons:
- **[Extend]** → Modal: enter days to extend. Calls `POST /api/admin/subscriptions/{sub_id}/extend`.
- **[Cancel]** → Confirmation modal with reason. Calls `POST /api/admin/subscriptions/{sub_id}/force-cancel`.
- **[Override Streak]** → Modal: enter new streak/cumulative values. Calls `PATCH /api/admin/subscriptions/{sub_id}/streak`.

### 6.4 Gift Subscription
Standalone action (above the table):
- Search for player → select → choose duration (default 30 days).
- Calls `POST /api/admin/subscriptions/{player_id}/gift`.

### 6.5 Subscription Metrics Cards

| Metric | Description |
|:---|:---|
| **Active Subscribers** | Count where `status = 'active'` |
| **Monthly / Annual Split** | Count by plan type |
| **Past Due** | Count where `status = 'past_due'` (grace period) |
| **Voluntary Churn (30d)** | `(actively_cancelled_last_30d / active_at_start_of_period) × 100` — player-initiated cancellations |
| **Involuntary Churn (30d)** | `(expired_nonrenewal_last_30d / active_at_start_of_period) × 100` — payment failure / non-renewal |
| **Total Churn (30d)** | Sum of voluntary + involuntary churn |
| **Conversion Rate** | `(total_ever_subscribed / total_players) × 100` |
| **MRR (Monthly Recurring Revenue)** | `(monthly_count × $1.99) + (annual_count × $19.90 / 12)` |

## 7. Tab 5: Shop Management

### 7.1 Shop Item Catalog
Full CRUD interface for `shop_items`:

**Item List View:**
- Paginated table with columns: ID, Icon, Name, Category, Price (Shards), Active, Featured, Sort Order, Actions
- Filterable by category (skin/flair/badge/avatar/booster/marketplace_permit/patron_*), active/inactive
- Searchable by name

**Create/Edit Item Modal:**
- Fields: item_key, name, description, category (dropdown), price_shards, icon_path, class_restriction, is_active, is_featured, featured_from/until (datetime pickers), available_from/until (datetime pickers), sort_order
- **For booster items** (category = 'booster'): structured form fields instead of raw JSON:
  - Boost Type (dropdown: xp, essence, drop_rate)
  - Duration (seconds, integer input)
  - Magnitude (decimal input, e.g. 1.25)
  - These are stored as `item_metadata` JSON: `{"boost_type": "xp", "duration_seconds": 3600, "magnitude": 1.25}`
- **For non-booster items:** read-only `item_metadata` display (rarely used)
- Preview card showing how the item will appear in the shop

**Delete (Soft):**
- Sets `is_active = false`. Confirmation required.

### 7.2 Bundle Management
Full CRUD for `shop_bundles`:

**Bundle List View:**
- Table: ID, Name, Price, Original Price, Discount %, Active, Contents (item count), Actions

**Create/Edit Bundle Modal:**
- Fields: bundle_key, name, description, price_shards, original_price_shards, discount_pct, icon_path, is_active, sort_order
- **Item Selector:** Multi-select from active shop items with search. Shows selected items with drag-to-reorder.
- Discount calculator: shows savings % based on price vs sum of individual items.

### 7.3 Featured Rotation Scheduler
A dedicated sub-section for managing the featured/limited-time item rotation:

- **Table view:** Simple table listing all items/bundles with featured windows (featured_from → featured_until), sorted by date.
- **Columns:** Item Name, Category, Featured From, Featured Until, Status (Active/Scheduled/Expired), Actions
- **Conflict detection:** Row warning highlight if too many items overlap in the same featured window.
- **Quick actions:** "Feature Now" (set featured_from = now, featured_until = now + 7d), "End Feature" (clear featured dates).

### 7.4 Booster Configuration
Dedicated section for booster-category items. Booster runtime data lives in `player_active_boosters` (fields: `boost_type`, `magnitude`, `duration_seconds`), seeded from `item_metadata` JSON on the `ShopItem`.

- Table of all booster items with: Name, Boost Type, Duration (seconds), Magnitude, Price (Shards), Active
- **Structured inline edit form** for booster properties:
  - Boost Type dropdown: xp, essence, drop_rate
  - Duration (seconds) input
  - Magnitude (decimal, e.g. 1.25) input
  - These update the `item_metadata` JSON on the `ShopItem` record
- Reference to `game_configs` booster keys (`shop_booster_max_stack`, `shop_booster_max_elapsed_per_ping`) with link to GameConfigs page.

### 7.5 Shop Purchase Analytics
Metrics specific to the shop:

| Metric | Description |
|:---|:---|
| **Total Items Sold** | Count of `player_shop_items` |
| **Revenue by Category** | Shards spent per category (skin, booster, bundle, etc.) |
| **Top Selling Items** | Top 10 items by purchase count |
| **Active Boosters** | Count of currently active player boosters |
| **Bundle Conversion** | % of bundle views that result in purchase (if tracking available) |

## 8. Tab 6: Marketplace Moderation

### 8.1 Active Listings
Paginated table of marketplace listings with admin controls:

| Column | Description |
|:---|:---|
| Listing ID | `marketplace_listings.id` |
| Seller | Player name + ID (clickable) |
| Item | Name + rarity badge + type (artifact/equipment) |
| Price | Shards |
| Status | active / sold / expired / cancelled |
| Listed At | Timestamp |
| Expires In | Countdown or "Expired" |
| Actions | [Force Remove] [View Seller] |

- Filterable by status, player, item type, price range, date range
- Searchable by item name, player name

### 8.2 Force Remove Listing
1. Admin clicks **[Force Remove]** on an active listing.
2. Confirmation modal: `"Remove listing for [ItemName]? The item will be returned to [SellerName]'s inventory and they will be notified."`
3. Requires **reason** text field.
4. Calls `DELETE /api/admin/marketplace/listings/{listing_id}`.

### 8.3 Trade History Audit
Paginated table of `marketplace_trades`:

| Column | Description |
|:---|:---|
| Trade ID | `marketplace_trades.id` |
| Buyer | Player name + ID |
| Seller | Player name + ID |
| Item | Name + rarity |
| Price | Shards |
| Tax | Tax burned |
| Seller Proceeds | Price - Tax |
| Date | `traded_at` |
| Actions | [Reverse Trade] [View Buyer] [View Seller] |

- Filterable by player, price range, date range
- Searchable by player name, item name

### 8.4 Reverse Trade
1. Admin clicks **[Reverse Trade]**.
2. Confirmation modal shows full trade details and warns: `"This will return the item to the seller, debit shards from the seller, and credit shards back to the buyer. Tax is NOT refunded."`
3. Requires **reason** text field.
4. Calls `POST /api/admin/marketplace/reverse-trade/{trade_id}`.

### 8.5 Marketplace Stats
Metrics cards (using existing `GET /api/admin/marketplace/stats` + new analytics):

| Metric | Description |
|:---|:---|
| **Active Listings** | Count of listings with `status = 'active'` |
| **Total Volume (All Time)** | Sum of `price_shards` from all trades |
| **Volume (7d / 30d)** | Recent trade volume |
| **Average Sale Price** | `AVG(price_shards)` from trades |
| **Tax Burned (All Time)** | Sum of `tax_shards` |
| **Unique Traders (30d)** | Distinct buyer + seller player IDs |
| **Items Listed (30d)** | Count of listings created in last 30 days |

### 8.6 Price Anomaly Detection
Automated flagging of suspicious marketplace activity:

- **High-price anomaly:** Listings priced at >10x the average price for the same item name/rarity in the last 30 days. Threshold configurable via `game_configs` key `anomaly_price_multiplier_threshold` (default: `10`).
- **Rapid relisting:** Same seller relisting same item type >5 times in 1 hour. Threshold configurable via `anomaly_rapid_relist_count` (default: `5`) and `anomaly_rapid_relist_window_minutes` (default: `60`).
- **Wash trading suspicion:** Same two players trading back and forth >3 times in 24 hours. Threshold configurable via `anomaly_wash_trade_count` (default: `3`) and `anomaly_wash_trade_window_hours` (default: `24`).

**Implementation:** Price anomaly checks run on-demand when the admin visits the Marketplace tab or clicks Refresh. Flagged anomalies are logged to `activity_events` with type `marketplace_price_anomaly`, `marketplace_rapid_relist`, or `marketplace_wash_trade_suspicion`. The admin views these via a filtered anomaly sub-table in the Marketplace tab.

**No automatic blocking.** Anomalies are informational — admin reviews and decides whether to act.

## 10. Tab 8: Dispute Queue

### 10.1 Flagged Account List
A focused view of accounts flagged due to Stripe disputes/chargebacks:

| Column | Description |
|:---|:---|
| Player | Display name + ID (clickable) |
| Flag | `account_flag` value |

| Actions | [Investigate] [Clear Flag] [Ban] [Warn] |

### 10.2 Investigation Panel
Clicking **[Investigate]** expands to show:

- **Donation History:** All donations
- **Account Flags:** Any prior dispute flags, warnings

### 10.3 Resolution Actions
- **[Clear Flag]:** Removes `account_flag`, re-enables trading/purchasing. Requires reason. Logged.
- **[Warn]:** Creates a regular notification in the player's notification feed (same `marketplace_notifications` pattern — or a general `player_notifications` equivalent). Sets a `warned_at` timestamp in activity_events. Does NOT change the account flag.
- **[Ban]:** Sets `account_flag = 'banned'`. Blocks all gameplay. Requires reason. Logged. (Uses existing player block mechanism from 1.0.)

## 13. Security Requirements

### 13.1 Authentication
- All `/api/admin/finance/*` endpoints require admin JWT authentication (`get_current_admin`).
- All actions are logged to `activity_events` and the audit log.

### 13.2 Stripe API Calls
- Stripe refund initiation requires the `STRIPE_SECRET_KEY` environment variable.
- Refund amounts are validated server-side (cannot exceed original charge amount minus existing refunds).
- Stripe API errors are caught and returned as structured error responses (not raw exceptions).

### 13.3 Shard Adjustment Safety
- All manual adjustments require a non-empty reason string.
- **No hard cap** on adjustment amounts. Large adjustments (>10,000 shards) show a soft warning confirmation: `"This is a large adjustment. Are you sure?"` but do not block.
- Adjustments are fully auditable via `shard_transactions` with `source_type = 'admin_grant'` or `'admin_deduct'`.

### 13.4 Dispute Resolution
- Banning a player is a high-severity action: requires double confirmation and is prominently logged.
- Flag clearing is logged with the admin's email and reason.

## 14. Error Handling

### 14.1 Stripe API Errors
- All Stripe API calls (refund initiation, reconciliation, polling) handle `stripe.error.StripeError` and return structured error messages.
- Network timeouts show: `"Stripe API is temporarily unavailable. Please try again."`

### 14.2 Stale Data
- If an admin attempts an action on a record that has changed since the page loaded (e.g., listing already removed), the backend returns 409 Conflict or 410 Gone, and the UI shows a "Data has changed, please refresh" message.

### 14.3 Large Result Sets
- All list views are paginated (default 25, max 100 per page).
- Analytics queries have configurable date range limits (max 365 days for charts).

## 17. Design Decisions (Resolved)

| # | Decision | Resolution |
|:---|:---|:---|
| 1 | Page structure | Single admin page with 8 tabs (not separate pages). Matches user preference for unified finance view. |
| 2 | Shard adjustment location | Both in Finance Dashboard (Tab 3) AND embedded in PlayerDetail page for contextual support. |
| 3 | Stripe refund from admin | Calls Stripe API directly to create refund, then auto-debits shards. Dual action (Stripe + internal). |
| 4 | Dispute queue complexity | Simple flagged account list with investigation panel. No workflow/assignment/status tracking. |
| 5 | Revenue analytics calculation | Server-side DB-driven aggregation (new endpoints). No client-side calculation from raw data. |
| 6 | Price anomaly handling | Detection runs on-demand (via analytics endpoint). Anomalies logged to activity_events for admin review. No automatic blocking. |
| 7 | Shop management depth | Full CRUD UI with featured rotation scheduling, booster inline config, and purchase analytics. Goes beyond 3.3's simple endpoint CRUD. |
| 8 | Refresh model | Manual refresh only (on load, on tab switch, on button click). No auto-polling. |
| 9 | Chart library | Reuse whatever the existing Dashboard.tsx uses for consistency. If none, pick a lightweight React-friendly library. |
| 10 | Shard adjustment cap | No hard cap. Soft warning at >10,000 shards. |
| 11 | Churn tracking | Track voluntary (player-initiated cancel) and involuntary (payment failure / non-renewal) separately AND combined total. |
| 12 | Featured rotation view | Simple table (not calendar/Gantt). Sorted by date with conflict highlighting. |
| 13 | Anomaly thresholds | All configurable via `game_configs`. Defaults: 10x price, 5 relists/hour, 3 wash trades/24h. |
| 14 | Player warnings | Regular notification in player feed. Not a blocking modal. |
| 15 | CSV export | All paginated list views support CSV export of the current filtered dataset. Client-side generation from loaded data. |
