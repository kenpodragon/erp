## 1. Inspirations & Design Baseline

Character progression is modeled after the following titles. Use them as a baseline for stat weight and growth feel:

| System | Inspiration | Key Features |
|:---|:---|:---|
| **Stat scaling & mixing** | *Magic Research 2* | Mix-and-match skill bonuses, resource interdependency, visible growth curves |
| **Skill depth & breadth** | *Melvor Idle* | Infinite long-term potential, prerequisite trees, offline-compatible passive growth |
| **Item generation** | *Path of Exile* (simplified) | Prefix/suffix procedural loot, rarity tiers, stat-gated equip requirements |
| **Class identity** | *Towers of Elysium* source IP | Class abilities are narrative-derived; every mechanic has a lore root |

These titles provide the baseline. The requirements below supersede them where they diverge.

## 2. Extensible Core Stats System *(Sub-phase: 2.4.0)*

- [ ] **2.2** Stat tables created and seeded (STR/AGI/INT) *(Schema §2, §3)*
- [ ] **2.3** Stat computation engine (`recalculate_character_stats`) operational *(Design §1.1–§1.6)*
- [ ] **2.4** Lore stat distribution working per class *(Design §1.4)*
- [ ] **2.5** Extensibility: new stat via DB insert works without code change

### 2.1 Design Goal

Stats must be **fully extensible via the database** — adding a new stat (e.g., Perception, Endurance) requires only a DB insert and admin configuration. No schema migrations or backend code changes are needed after the 2.4 foundation tables are in place.

### 2.2 Initial Stats (Rule of 4 baseline)

| Stat | Display Name | Story Mode Effects | Formulas (all coefficients in `game_configs`, DB-configurable) |
|:---|:---|:---|:---|
| **Strength** | STR | Click damage floor, physical resistance | `click_damage = base × (1 + STR × str_damage_coeff)`, incoming boss damage reduced |
| **Agility** | AGI | Auto-DPS multiplier, critical hit chance | `auto_dps = base × (1 + AGI × agi_speed_coeff)`, `crit_chance = base_crit + AGI × agi_crit_coeff` |
| **Intelligence** | INT | Hotbar skill power, cooldown reduction | `skill_power × (1 + INT × int_power_coeff)`, `cooldown = base × max(0.5, 1 - INT × int_cd_coeff)` |

> **Extensibility:** New stats added via DB inserts can define their own Story Mode effects by registering new `effect_type` entries in `benefit_effect_data`. Frontend handlers for new effect types require a code update — see Design doc §1.7.

> **Note:** The Lore idle skill is not a core stat — it distributes bonus points to the primary and secondary stats of the character's class (see §2.4).

### 2.3 Stat Sources (Hybrid Model)

Every character's stats are computed from the sum of all sources at session start and on equip/unequip. Sources:

| Source | Mechanism |
|:---|:---|
| **Class base** | Fixed base values per stat defined in `class_stat_affinities` |
| **Idle Training: Attack** | Contributes directly to Strength |
| **Idle Training: Precision** | Contributes directly to Agility |
| **Idle Training: Magic** | Contributes directly to Intelligence |
| **Idle Training: Lore** | Distributes bonus to primary + secondary stat (class-dependent, see §2.4) |
| **Character level** | Flat additive bonus per level on the character's primary stat (class-dependent) |
| **Equipped items** | Stat bonuses from `player_inventory` items with `is_equipped = TRUE` |

### 2.4 Lore Stat Distribution by Class

The Lore idle skill's contribution is split between a character's primary and secondary stats, determined by their class:

| Class | Primary Stat (Lore bonus weight) | Secondary Stat (Lore bonus weight) |
|:---|:---|:---|
| **Drifter** | Strength (60%) | Agility (40%) |
| **Engineer** | Agility (60%) | Strength (40%) |
| **Conduit** | Intelligence (60%) | Agility (40%) |
| **Vessel** | All three stats equally (33% / 33% / 33%) |

*Exact coefficients are in the Design doc §2. All weights are configurable per class in `class_stat_affinities`.*

### 2.5 Extensibility Contract

New stats are added without code changes by:

1. Insert a row into `stat_definitions` (name, display_name, formula hints, category).
2. Map idle skill contributions in `idle_skill_stat_contributions` (idle skill → stat ID, coefficient).
3. Configure class base values and Lore distribution weights in `class_stat_affinities`.
4. The stat display, calculation engine, and admin editor all read from these tables dynamically.

## 3. Character Level System *(Sub-phase: 2.4.0)*

- [x] **3.1** Character XP accrual from idle training + scene completion *(Design §2.1)*
- [x] **3.2** Quadratic level-up curve operational *(Design §2.2–§2.3)*
- [x] **3.3** Level-up stat bonuses applied per class *(Design §1.5)*
- [x] **3.4** `recommended_level` seeded for all chapters *(Schema §3.5)*
- [x] **3.4** `min_level` hard gate enforced on session start

### 3.1 Overview

Character Level is a **visible, permanent level** displayed on the character sheet. It represents the character's overall growth across both idle training and story mode — not any single skill's progress.

- **Cap:** Level 99 (matching idle skill cap; extensible via game_configs).
- **Visible to:** player and other players (on leaderboard/profile).

### 3.2 Character XP Sources

| Source | XP Contribution |
|:---|:---|
| **Idle Training XP earned** | A configurable fraction of all idle XP earned converts to Character XP (ratio in `game_configs`) |
| **Story Mode scene completion** | Flat Character XP per scene cleared (configurable per scene difficulty) |

> Character XP from both sources accumulates permanently. There is no cap on daily Character XP gains.

### 3.3 Level-Up Grants

On each character level-up:
- Flat additive bonus to the class's **primary stat**.
- Smaller additive bonus to the class's **secondary stat** (every other level).
- Bonus amounts are configurable in `game_configs`.
- A level-up notification fires in the UI (consistent with idle skill level-up display).

### 3.4 Content Level Requirements

Chapters and books may have configurable level requirements stored in the DB and editable in admin:

| Field | Type | Behavior |
|:---|:---|:---|
| `recommended_level` | INTEGER | Advisory — displayed as a suggested level before entry; no hard block |
| `min_level` | INTEGER | Hard gate — player cannot start the scene/chapter below this level |

- Items also carry `min_char_level` requirements (see §6.5).
- Skill prerequisites may reference character level (see §5.2).

### 4.1 Classes (Rule of 4)

| Class | Primary Stat | Idle Affinity Skill | Class-Exclusive Skill | Design Philosophy |
|:---|:---|:---|:---|:---|
| **Drifter** | Strength | Attack | **Threshold Slip** — increases crit chance | Speed & stealth; strikes from impossible angles |
| **Engineer** | Agility | Precision | **Energy Shields** — reduces incoming damage | Defense & construction; bends the prison's mechanisms |
| **Conduit** | Intelligence | Magic | **Akashic Cascade** — AOE damage burst | Offense & cosmic magic; channels raw Akashic energy |
| **Vessel** | All (balanced) | Lore | **Elder Fury** — temporary damage multiplier | Power & divine fury; knowledge-keeper of cosmic entities |

### 4.2 Class-Specific Skills (Beyond the 9 Hotbar)

Each class has **1 class-exclusive hotbar skill** for the initial release (expandable later via DB insert):

- **Only appear** for characters of that class (invisible to others).
- Require **stat + character level + idle skill** unlock prerequisites (AND-gated).
- Provide lore-accurate boosts aligned with that class's narrative role.
- **Displayed in a dedicated second hotbar row** below the 9 universal skills, with class-themed styling per class.
- Follow the same **dual-leveling system** (idle training + session gold) and Level 0 system as universal skills (§5.1a).
- Each has its own **idle training action** with lore-appropriate flavor text.

| Class | Skill | Effect Type | Idle Training Action | Lore Basis |
|:---|:---|:---|:---|:---|
| **Drifter** | Threshold Slip | `crit_boost` | "Walking the Threshold" | Liminal-space navigation, memory erasure |
| **Engineer** | Energy Shields | `damage_reduction` | "Substrate Reconstruction Drills" | Eternal Engine, substrate manipulation |
| **Conduit** | Akashic Cascade | `aoe_burst` | "Lucid Conduit Channeling" | Dreamscape conduits, Akashic Flow |
| **Vessel** | Elder Fury | `damage_multiplier` | "Channeling Tiamat's Coils" | Divine entity channeling, Shepherd Initiative |

### 4.3 Class-Stat Configuration (DB-Driven)

All class-to-stat mappings are stored in `class_stat_affinities`:
- `primary_stat_id`, `secondary_stat_id`
- `lore_primary_weight`, `lore_secondary_weight` (floats summing to 1.0)
- `char_level_primary_bonus`, `char_level_secondary_bonus` (per-level flat additions)
- Future classes added via DB insert only — no code changes.

### 4.4 Class Visual Identity System

Each class has a distinct visual identity that permeates the UI in both the Hub and Story Mode. All visual configuration is stored as **JSONB** (`visual_config`) on the `character_classes` table, admin-editable and extensible without code changes for new color/style tweaks.

**Visual elements applied per class:**

| Element | Where Applied | Example |
|:---|:---|:---|
| **Primary color** | Hero stats panel border/glow, hotbar skill borders, class skill row accent | Drifter = crimson, Engineer = steel blue |
| **Secondary color** | Health bar fill, session gold counter accent | Complementary shade of primary |
| **Damage text color** | Click damage numbers in PixiJS combat canvas | Class-themed color for click damage floaters |
| **Skill activation particles** | PixiJS particle burst on hotbar skill use | Class-colored particle tint |
| **Avatar/portrait** | Hero panel avatar frame, character sheet header | `avatar_url` key in visual_config (asset path) |
| **Idle animation tint** | PixiJS canvas player entity sprite | Light class-colored tint overlay |

**JSONB schema (stored in `character_classes.visual_config`):**

```json
{
  "primary_color": "#DC143C",
  "secondary_color": "#8B0000",
  "damage_text_color": "#FF6B6B",
  "particle_tint": "#FF4444",
  "avatar_url": "/assets/classes/drifter_avatar.png",
  "border_glow_intensity": 0.6,
  "idle_sprite_tint": "#FFCCCC"
}
```

> **Admin CRUD:** Classes are fully manageable from the admin Content Editor (§7.2) — create new classes, edit stat affinities, skills, and visual config. New classes are immediately available for character creation with no code deployment.

> **Frontend consumption:** The frontend reads `visual_config` from the character's class at session start and applies CSS custom properties (`--class-primary`, `--class-secondary`, etc.) to the game UI container. PixiJS tints are applied via the existing `tint` property on sprites and text objects.

## 5. Unified Skill System *(Sub-phase: 2.4.1)*

- [ ] **5.1** Level 0 system enforced for all non-Attack skills *(Design §3.1)*
- [ ] **5.1a** Dual-leveling (idle + session) operational for active skills *(Design §3.2)*
- [ ] **5.1a** 13 active skill idle training actions seeded *(Schema §5.4)*
- [ ] **5.2** Prerequisite evaluation (AND-gate, all 5 types) operational *(Design §5.1)*
- [ ] **5.3** Prerequisite display rules implemented (Idle panel + UpgradeMenu)
- [ ] **5.4** Admin prerequisite editor operational *(Req §7.2)*

### 5.1 Level 0 — The Locked State

All skills **except Attack** begin at **Level 0** (locked). This applies to:
- All idle training skills (Magic, Lore, Precision)
- All universal hotbar/active skills (Clickstorm, Powersurge, etc.)
- All class-exclusive skills

**Level 0 → Level 1 behavior:**
- Has a custom, **higher XP requirement** than the standard idle curve (configurable per skill via `skills.level_0_xp_requirement`).
- The skill is **invisible** in all UIs (Idle Training panel, Story Mode UpgradeMenu, skill trees) until prerequisites are met.
- Once prerequisites are met, the skill becomes **visible but locked** with a "Train to Level 1 to unlock" prompt.
- Once Level 1 is reached in the **idle skill tree**, the corresponding active skill becomes **purchasable** in Story Mode.

**Attack exception:**
- Attack idle skill starts at Level 1 (not 0) — available from game start.
- Universal active skills that require only Attack prerequisites can be purchased in session immediately.

### 5.1a Dual-Leveling System (Active/Hotbar Skills)

Active skills have **two independent levels** that work together:

| Level Type | Where It's Trained | Persistence | Purpose |
|:---|:---|:---|:---|
| **Idle Level** (0–99) | Idle Training panel | Permanent | Sets the skill's **base power tier** (e.g., Clickstorm idle lvl 1 = 1 click/sec, idle lvl 10 = 2 clicks/sec) |
| **Session Level** (1+) | Story Mode UpgradeMenu (gold) | Per-session (resets) | Multiplies on top of the idle base (standard gold upgrade scaling) |

**Full lifecycle of an active skill (e.g., Clickstorm):**
1. Prerequisites unmet → skill invisible everywhere
2. Prerequisites met → appears in Idle Training panel at Level 0
3. Player trains idle Level 0→1 (uses `level_0_xp_requirement` XP, higher than normal)
4. Player continues idle training levels 1→99 (standard XP curve, level 99 cap — same as core idle skills)
5. In Story Mode: skill appears in UpgradeMenu at Session Level 0 (locked, costs gold)
6. Player buys Session Level 1 → skill becomes usable with base power = f(idle_level)
7. Session Levels 2+ → gold upgrades multiply on top of idle-scaled base

**Each active skill has its own idle training action** with lore-appropriate flavor text (e.g., Clickstorm → "Tempo Drilling", Powersurge → "Resonance Channeling"). These are seeded in `skill_actions`.

**Idle level → base power scaling** is configurable per skill via `skills.idle_level_scaling` (JSONB). The frontend reads this to compute the skill's base effectiveness at the current idle level.

### 5.2 Unified Prerequisite System

All skills (idle and active) use a single `skill_prerequisites` table that supports multiple prerequisite types. All prerequisites on a skill are **AND-gated** — every condition must be satisfied.

**Prerequisite types:**

| Type | What it checks | Example |
|:---|:---|:---|
| `idle_skill_level` | Minimum level in an idle skill (Attack/Magic/Lore/Precision) | `idle: Attack ≥ 10` |
| `active_skill_level` | Minimum level of another active/hotbar skill | `active: Clickstorm ≥ 5` |
| `stat_value` | Minimum computed stat value (Str/Agi/Int or any future stat) | `stat: Intelligence ≥ 40` |
| `character_level` | Minimum character level | `char_level ≥ 20` |
| `scene_cleared` | Story Mode scene must be completed | `scene: ch1_dreamwalking_cleared` |

**Illustrative prerequisite chains (not final values):**

| Skill | Prerequisites |
|:---|:---|
| Attack (idle) | None — available at game start |
| Clickstorm (active) | `idle: Attack ≥ 10` |
| Magic (idle) | `scene: first_dreamwalking_scene` |
| Powersurge (active) | `idle: Magic ≥ 10`, `active: Clickstorm ≥ 1` |
| Lucky Strikes (active) | `idle: Precision ≥ 18` |
| Super Clicks (active) | `idle: Attack ≥ 25`, `active: Clickstorm ≥ 10` |
| Conduit Class Skill 1 | `char_level ≥ 15`, `stat: Intelligence ≥ 50`, `idle: Magic ≥ 30` |

*All values are configurable via admin. See Design doc §5 for the full initial prerequisite tree.*

### 5.3 Prerequisite Display Rules

- **In Idle Training panel:** Skills with unmet prerequisites show a "LOCKED" state listing each unmet condition.
- **In Story Mode UpgradeMenu:** Skills below Level 1 in idle are hidden. Skills with met idle prerequisites but unmet active prerequisites show "LOCKED — [requirement]".
- **Class-exclusive skills:** Hidden entirely for characters of the wrong class.

### 5.4 Admin Configurability

All prerequisites are stored in the DB and editable via the admin content editor (§8). No code changes are required to add, modify, or remove prerequisites.

## 6. Dream Item System *(Sub-phase: 2.4.2)*

- [ ] **6.2** Run achievement evaluator operational *(Design §6)*
- [ ] **6.3** Item generator (5-component code, stats, rarity) operational *(Design §4)*
- [ ] **6.3** `regenerate_item_names` admin utility implemented
- [ ] **6.4** Rarity weights configurable per book *(Design §4.4)*
- [ ] **6.6** PostBattleSummary loot UX (dice spin, Yaldabaoth, auto-placement) *(Design §6.3)*
- [ ] **6.6** Home Base inventory UI (3 equipped + 10 bag + equip/unequip/swap)
- [ ] **6.7** All item component tables seeded with lore-accurate content *(Schema §7)*

### 6.1 System Overview

Items in ERP are **procedurally generated "Dream Items"** — rare rewards earned through notable performance during Story Mode runs. They feel earned, not grinded. There is no shop, vendor, or crafting.

Players receive a generated item at the end of a qualifying run. They must **choose to keep it or dismiss it forever**. If their inventory is full, they must delete an existing item to make room.

### 6.2 Drop Trigger — Run Achievements

At the conclusion of every Story Mode scene run, the backend evaluates the player's run stats against a set of configurable achievement thresholds stored in `game_configs`:

| Achievement | Threshold (configurable) | Drop Chance (configurable) |
|:---|:---|:---|
| Speed Completion | Completed in under N minutes | X% |
| Enemy Slayer | Killed N or more enemies | X% |
| Wave Climber | Reached wave N or higher | X% |
| Perfect Run | Zero deaths during the run | X% |
| Boss Slayer | Defeated the scene/chapter boss | X% |
| High Tide | Reached a personal best wave for the scene | X% |

- Each satisfied achievement rolls **independently** — a single run can trigger multiple drops.
- If multiple items drop, they are presented one at a time (keep or dismiss each).
- All thresholds and percentages are stored in `game_configs` as a structured JSON block (key: `run_achievement_config`). Admin-editable.

### 6.3 Random Item Generator

Items are procedurally generated using a **5-component code** stored as the item's canonical identifier:

```
{PREFIX_CODE}_{QUALITY_CODE}_{LORE_TAG_CODE}_{ITEM_TYPE_CODE}_{SUFFIX_CODE}
```

**Display format:** `[Prefix] [Quality] [Lore Tag] [Item Type] of [Suffix]`

**Example:**
```
SOLAR_ELDER_INFINITRON_BLADE_ASCENDANT
→ "Solar Elder Infinitron Blade of the Ascendant  (Level 12)"
```

**Generation steps (backend):**
1. Determine the **gear slot** (Weapon / Armor / Trinket) — weighted by scene chapter lore (e.g., combat-heavy scenes weight toward Weapon).
2. Roll **rarity** (Common → Cosmic) using weighted probability table (see §6.4).
3. Select **item_type** from `item_type_bases` for the rolled gear slot.
4. Select **prefix**, **quality**, **lore_tag**, **suffix** from their respective seeded tables.
5. Compute **base stats** from `item_type_bases.base_stat_range` × rarity multiplier.
6. Apply **prefix and suffix stat contributions** from their respective tables.
7. Set **item level** = min(chapter.recommended_level, character_level). Never exceeds the chapter's recommended level.
8. Compute `min_char_level` and `stat_requirements` from item level and rarity (see Design doc §4).
9. **Assemble and store the display name** in `inventory_items.name` (denormalized at creation time from the 5 components). The `item_code` is the canonical source of truth; `name` is pre-computed for fast reads and sorting.
10. Store the item code in `inventory_items.item_code`.

> **Remediation:** A backend admin utility can regenerate all display names from `item_code` if component table names change (e.g., if "Solar" is renamed to "Stellar" in `item_prefixes`).

### 6.4 Rarity Tiers

| Rarity | Color | Default Drop Weight | Stat Multiplier |
|:---|:---|:---|:---|
| Common | Grey | 55% | 1.0× |
| Uncommon | Green | 25% | 1.3× |
| Rare | Blue | 12% | 1.7× |
| Epic | Purple | 6% | 2.2× |
| Cosmic | Gold | 2% | 3.0× |

Weights are configurable in `game_configs`. Higher-difficulty chapters (later books) can shift the distribution toward rarer drops.

### 6.5 Item Requirements

Each generated item carries:
- `min_char_level` — minimum character level required to equip.
- `stat_requirements` (JSONB) — minimum stat values required to equip (e.g., `{"strength": 30}`).
- Items that fail requirements display as "LOCKED" in inventory with the specific unmet conditions shown.

### 6.6 Inventory Rules

| Slot Category | Count | Behavior |
|:---|:---|:---|
| Equipped slots | 3 (Weapon, Armor, Trinket) | Always active; affect live stats |
| Inventory slots | 10 (unequipped storage) | Swappable from Home Base only |
| **Total capacity** | **13** | Hard cap |

- **Access:** Inventory is only accessible from **Home Base** — cannot be managed during Story Mode.
- **Dream item loot section:** Integrated into the **PostBattleSummary** screen. For each run achievement cleared, a **dice spin animation** plays:
  - **Failed roll:** Thundercloud with Yaldabaoth laughing behind it, then fades away (no drop).
  - **Successful roll:** Item materializes with rarity-colored border, item sprite, name, and stats/bonus effects on hover.
  - Multiple achievements roll sequentially (dice 1 → dice 2 → dice 3).
- **Auto-placement priority:** When an item drops:
  1. If the matching equipped gear slot is empty → **auto-equip**.
  2. If equipped slot is full but bag has space → **goes to bag**.
  3. If everything is full → **comparison UI**: player sees their current items (FIFO left-to-right) and picks one to replace or discards the new item.
- **Equipping/unequipping:** Done from Home Base inventory UI. **Direct swap:** equipping from bag when a slot is occupied atomically swaps the two items (bag→equipped, equipped→bag). No intermediate "unequip first" step required. Net bag count unchanged.

### 6.7 Lore Seeding Requirements

All item generation component tables must be seeded with **lore-accurate content** from the Towers of Elysium trilogy. Initial seed targets:

| Table | Min Seed Count | Examples |
|:---|:---|:---|
| `item_prefixes` | 20+ | Solar, Void, Quantum, Elysian, Nanite, Spectral, Temporal, Corrupted, Prismatic, Fractured |
| `item_qualities` | 10+ | Elder, Proto, Resonant, Calibrated, Corrupted, Phase-Locked, Hyper-Dense, Crystalline, Stabilized |
| `item_lore_tags` | 15+ | Infinitron, Threshold, Dreamscape, Etheris, Akashic, Substrate, Conduit, Shepherd, Pointer, Aspolin |
| `item_type_bases` (Weapon) | 6+ | Blade, Emitter, Gauntlet, Staff, Resonance Fork, Pulse Cannon |
| `item_type_bases` (Armor) | 5+ | Shielding, Conduit Weave, Nanite Plating, Drift Cloak, Barrier Lattice |
| `item_type_bases` (Trinket) | 5+ | Crystal, Module, Fragment, Sigil, Lens |
| `item_suffixes` | 20+ | the Aspolin, Eternal Purpose, the Void, the Construct, the First Key, the Elysian Accord, the Threshold |

*Exact lore-accurate names to be finalized in Design doc §5 via lore research.*

## 7. Admin Panel — 2.4 Scope *(Sub-phase: 2.4.3)*

- [ ] **7.1** Config browser (searchable, read-only with metadata)
- [ ] **7.2** Content editor CRUD: stats, classes, skills, prerequisites, benefits, item components
- [ ] **7.3** Effect-type system: frontend handler map for all skill/item effect types *(Design §8.3)*

Two distinct admin features are delivered in 2.4. The full individual key editor for game/server configs is deferred to Admin Panel 5 (later requirement).

### 7.1 Config Browser (game_configs + server_config)

A searchable, read-annotated panel for all configuration keys:

- **Search:** Filter by key name, category, or game_impact text.
- **Display per key:** `key`, `value` (read-only), `description`, `game_impact` (which screens/formulas/calculations are affected), `category`, `last_modified_at`, `modified_by`.
- **2.4 scope:** Adding `description`, `game_impact`, and `category` columns to both config tables. Values are read-only here — editing deferred to Admin Panel 5.
- **Use case:** Developers and admins can understand what each config does without digging into code.

### 7.2 Content Editor

Full CRUD admin interface for all game content tables (no code deployment needed to add/edit content):

| Entity | Operations | Key Fields |
|:---|:---|:---|
| **Stats** (`stat_definitions`) | Create, edit, delete | name, display_name, value_type, category, description |
| **Classes** (`character_classes` + `class_stat_affinities`) | **Create**/Edit/Delete class details + stat affinities + visual config | base values, Lore weights, primary/secondary stat mappings, `visual_config` JSONB (colors, avatar, particle tints) |
| **Idle Skills** | Edit all skill properties | name, description, level_0_xp_requirement, unlock gates |
| **Skill Actions** | Edit action XP, intervals, lore text | xp_per_action, interval_ms, display_name, lore_context |
| **Active/Hotbar Skills** | Create/edit universal and class-exclusive skills | name, class_id (if exclusive), description, effect_type, benefits_json |
| **Skill Prerequisites** | Add/remove/edit prerequisites on any skill | prerequisite_type, ref_id, min_value |
| **Benefits & Effects** (`benefit_effect_data`) | CRUD | effect_key, display_name, description, value_type |
| **Item Components** (prefixes, suffixes, types, etc.) | CRUD + seed management | All item generation table rows |

### 7.3 Effect-Type System (Hybrid Approach)

Skills and items reference effect types from the `benefit_effect_data` table. The frontend maintains a **handler map** (`effect_type → renderer/behavior function`) for all known effect types.

- **Existing effect types** (from the 9 universal + 4 class skills ≈ 10 distinct types: `click_burst`, `damage_multiplier`, `dps_boost`, `gold_multiplier`, `cooldown_reduction`, `aoe_burst`, `shield`, `crit_boost`, etc.) work without code changes — admins can create new skills using these types.
- **Truly novel mechanics** require a frontend code update to add the new handler, but the new handler is then reusable for future skills.
- **Developer guide:** See Design doc §8.3 for instructions on adding new effect types (DB registration + frontend handler).
