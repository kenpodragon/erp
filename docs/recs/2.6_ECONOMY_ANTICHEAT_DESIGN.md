## 1. Animation Toggle (Reduce Motion)

### 1.1 Persistence Model

The `reduce_motion` preference is stored in the existing `player.settings` JSONB column (no migration needed for the column itself — it already exists).

```json
// player.settings JSONB
{
  "audio": { "master_volume": 0.8, ... },
  "reduce_motion": true
}
```

**Sync:** `PATCH /api/players/me/settings` (existing endpoint). Also cached in `localStorage` for immediate access before API response.

### 1.2 CSS Integration

```
Priority chain:
1. User's explicit toggle (player.settings.reduce_motion) — highest priority
2. OS-level prefers-reduced-motion media query — baseline default
3. If neither set, motion is ON (default behavior)
```

Implementation:
- A CSS class `.reduce-motion` is applied to `<body>` when the toggle is active.
- All animation-related CSS uses:
  ```css
  @media (prefers-reduced-motion: reduce) { /* baseline */ }
  body.reduce-motion { /* explicit override */ }
  ```

### 1.3 Component Suppression Map

| Component | Normal Behavior | Reduce Motion Behavior |
| :--- | :--- | :--- |
| `BottomAnimatedBanner` | Full PixiJS animation | Replaced with static bar (class icon + level text, dark panel) |
| `CombatStage` floating damage | Animated rise + fade | Hidden |
| `CombatStage` coin particles | Particle burst on kill | Hidden |
| `CombatStage` screen shake | Canvas offset on crit | Disabled |
| `SkillsHotbar` skill effects | Glow/pulse on activation | Static highlight only |
| `GoldOdometer` counter roll | Animated digit scroll | Instant value update |
| `PostBattleSummary` dice spin | Animated loot reveal | Instant reveal |
| `NarrativeReveal` star particles | 40 animated particles | Hidden |
| `BossStage` interrupt VFX | Animated zones | Static indicators |

### 1.4 Implementation Notes

- The `BottomAnimatedBanner` is a 510-line PixiJS component. When reduce motion is active, skip the entire component mount to avoid unnecessary WebGL context creation. Replace with a lightweight static bar showing `[ClassIcon] CharacterName Lv.{level}` — dark panel, no animation, same height as the banner to maintain layout consistency.
- The `CombatStage` PixiJS canvas remains active (gameplay still works); only decorative effects are suppressed via a `reduceMotion` prop passed from the settings context.
- `GoldOdometer` switches from `requestAnimationFrame` digit animation to direct value assignment.

## 2. Anti-Cheat Hardening

### 2.1 Wave Completion Validation

Added to the existing `/tick` endpoint after CPS validation:

```
Algorithm — Theoretical DPS Ceiling:
1. Calculate current auto DPS from character skill levels:
   current_auto_dps = _calc_auto_dps(session, character_id)

2. Project "best case" auto DPS after X waves:
   - Assume player puts ALL gold from X waves into auto_dps upgrades
   - projected_auto_dps = current_auto_dps + (total_gold_from_waves × upgrade_efficiency)

3. Calculate max click DPS:
   max_click_dps = click_damage_at_max_upgrade × cps_cap
   - Where click_damage_at_max_upgrade assumes ALL remaining gold goes to click upgrades

4. Combine for theoretical ceiling:
   theoretical_max_dps = max_click_dps + projected_auto_dps

5. Calculate max clearable waves per minute (decaying):
   - Since mobs scale exponentially, wave clear rate decays over time
   - For each zone z: time_to_clear(z) = _calc_zone_hp(z, scaling) / theoretical_max_dps
   - Sum time_to_clear for z = 1..N until total exceeds session_duration
   - This gives max_plausible_waves

6. Apply tolerance multiplier:
   max_waves = max_plausible_waves × wave_validation_tolerance

7. Use the SMALLER of:
   - max_waves (theoretical ceiling)
   - waves_completed_delta (reported by client)

8. If waves_completed_delta > max_waves:
   - Clamp waves_completed_delta to max_waves
   - Recalculate gold_delta based on clamped waves
   - Log anomaly to activity_events
```

**Configurable values (`game_configs`):**
| Key | Default | Description |
| :--- | :--- | :--- |
| `wave_validation_tolerance` | `2.0` | Multiplier buffer on top of theoretical ceiling |

**Edge cases:**
- First tick of a session uses a larger tolerance (3x) since initial state may have accumulated auto-DPS.
- The projection is deliberately generous — we want to catch blatant cheating, not penalize skilled play.

### 2.2 Session Integrity Check at `/complete`

```
Algorithm:
1. session_duration_s = (now - session.created_at).total_seconds()
2. max_gold_per_second = _calc_zone_gold(session.current_zone) × max_waves_per_second
   where max_waves_per_second = max_dps / _calc_zone_hp(session.current_zone, hp_scaling)
3. plausible_max_gold = max_gold_per_second × session_duration_s × session_gold_tolerance
4. If session.session_gold > plausible_max_gold:
   - Correct session_gold to plausible_max_gold
   - Log anomaly to activity_events
   - Recalculate essence conversion based on corrected gold
```

**Configurable values (`game_configs`):**
| Key | Default | Description |
| :--- | :--- | :--- |
| `session_gold_tolerance` | `3.0` | Multiplier buffer for session gold plausibility |

### 2.3 Anomaly Logging

All anomalies logged to `activity_events` (existing table) with:

```json
{
  "event_type": "anti_cheat_anomaly",
  "player_id": 123,
  "metadata": {
    "anomaly_type": "cps_violation|gold_correction|wave_clamp|session_integrity",
    "session_id": "uuid",
    "reported_value": 500,
    "corrected_value": 100,
    "zone": 15,
    "elapsed_ms": 1000
  }
}
```

No new tables needed. The existing `activity_events` table has `event_type` and `metadata` JSONB columns.

### 2.4 Two-Tier CPS UI Feedback

**Frontend state machine:**
```
States:
  NORMAL → cps_valid: true in tick response
  FLASHING → cps_valid: false in tick response (immediate)
  WARNING → cps_valid: false sustained for cps_warning_threshold_seconds
  COOLDOWN → was in WARNING, now receiving valid ticks (reset after cooldown period)

Transitions:
  NORMAL + invalid tick → FLASHING (GoldOdometer border turns red)
  FLASHING + invalid tick sustained → WARNING (toast appears)
  WARNING + valid tick for cooldown_s → NORMAL (toast fades)
  FLASHING + valid tick → NORMAL (red flash clears)
```

**Configurable values (`game_configs`):**
| Key | Default | Description |
| :--- | :--- | :--- |
| `cps_warning_threshold_seconds` | `5` | Seconds of sustained CPS violations before toast |
| `cps_warning_cooldown_seconds` | `10` | Seconds of valid CPS before clearing warning state |

## 3. Discovery System (Akashic Records)

### 3.1 Entity Discovery — Data Model

**New table: `player_entity_discovery`** (replaces the JSONB approach from the legacy design — proper relational table for better querying and indexing):

| Column | Type | Description |
| :--- | :--- | :--- |
| `id` | `SERIAL PK` | |
| `player_id` | `INTEGER FK` | FK to `players` |
| `entity_id` | `INTEGER FK` | FK to `entities` |
| `encounters` | `INTEGER` | Times this entity was seen (spawned in a wave) |
| `kills` | `INTEGER` | Times this entity was killed |
| `rank` | `VARCHAR(2)` | Current rank: `E`, `C`, `A`, `SS` (computed from kills) |
| `first_seen_at` | `TIMESTAMPTZ` | When the player first encountered this entity |
| `is_new` | `BOOLEAN` | Badge flag, cleared on hover/view in Codex |
| `UNIQUE` | | `(player_id, entity_id)` |

**Why not JSONB?** The legacy design used `registry_kills` JSONB on `player_progress`. With two-level tracking (per-variant + per-type aggregation) and ranked reveals, a proper table is cleaner for:
- Indexed queries by entity, player, or rank
- Aggregate queries for type roll-ups
- Avoiding JSONB race conditions entirely

### 3.2 Item & Skill Discovery — Data Model

**New table: `player_discovery_log`**

| Column | Type | Description |
| :--- | :--- | :--- |
| `id` | `SERIAL PK` | |
| `player_id` | `INTEGER FK` | FK to `players` |
| `discovery_type` | `VARCHAR(20)` | `skill`, `item_prefix`, `item_suffix`, `item_quality`, `lore_tag`, `effect` |
| `reference_id` | `INTEGER` | FK to the relevant table (skill_id, prefix_id, etc.) |
| `discovered_at` | `TIMESTAMPTZ` | When first discovered |
| `is_new` | `BOOLEAN` | Badge flag, cleared on hover/view in Library |
| `UNIQUE` | | `(player_id, discovery_type, reference_id)` |

### 3.3 Entity Family Grouping & Aggregation

A new `entity_family` column on the `entities` table provides species/family grouping (e.g., "Wraith", "Golem", "Shade"). This is distinct from the existing `entity_type` column which tracks combat role (creature, boss, miniboss, etc.).

**Migration:** `ALTER TABLE entities ADD COLUMN entity_family VARCHAR(100);`

**Population:** One-time classification pass via a tool script (`tools/classify_entity_families.py`) that parses `canonical_name` patterns and assigns families. Manual review and SQL corrections after the initial pass.

```
Aggregation query (per-family view):
SELECT
  e.entity_family,
  e.entity_type,
  COUNT(DISTINCT e.id) AS total_variants,
  COUNT(DISTINCT ped.entity_id) FILTER (WHERE ped.encounters > 0) AS discovered_variants,
  SUM(ped.kills) AS total_kills
FROM entities e
LEFT JOIN player_entity_discovery ped
  ON ped.entity_id = e.id AND ped.player_id = :player_id
WHERE e.entity_family IS NOT NULL
GROUP BY e.entity_family, e.entity_type
```

Entities with `entity_family = NULL` appear as standalone entries in the Codex (no family grouping).

### 3.4 Visibility Logic (Backend)

```
For each entity in a chapter:
  IF player has NOT reached this chapter:
    status = "mist" (completely hidden)
  ELSE IF player has reached/passed this chapter BUT encounters == 0:
    status = "grey" (blurred silhouette, name hidden)
  ELSE:
    status = "revealed" (name + rank-appropriate details shown)
```

"Reached" means the player's `player_progress.chapter_number >= entity's chapter`. For entities with no scene association (rare spawns), they default to "mist" until encountered.

### 3.5 Rank Reveal Mapping

| Rank | Kill Threshold | Reveals |
| :--- | :--- | :--- |
| Unranked | 0 kills (encountered only) | Silhouette visible, no details |
| E | 1 kill | Name, image, basic lore |
| C | `codex_rank_c` (default: 25) | Base HP, gold drops |
| A | `codex_rank_a` (default: 100) | Full stat block (Atk, Def, etc.) |
| SS | `codex_rank_ss` (default: 500) | Hidden lore secrets, completion badge |

Rank is computed on read (not stored), based on kill count vs. thresholds from `game_configs`. The `rank` column in `player_entity_discovery` is a denormalized cache updated on each kill for fast filtering/sorting.

### 3.6 Discovery Data Delivery

Discovery data is **piggybacked onto the existing `/tick` endpoint** to prevent data loss if the player disconnects mid-session (e.g., closes browser while farming). The `/tick` request payload is extended with optional discovery fields:

```
POST /api/game/story/session/{session_id}/tick
Body (extended):
{
  // Existing tick fields:
  "clicks": 45,
  "elapsed_ms": 1000,
  "zone": 5,
  "wave": 3,
  "gold_delta": 150.0,
  "waves_completed_delta": 2,

  // New discovery fields (optional, sent when there are new encounters):
  "entity_encounters": [
    { "entity_id": 42, "encounters": 3, "kills": 2 },
    { "entity_id": 99, "encounters": 1, "kills": 1 }
  ],
  "item_discoveries": [
    { "type": "item_prefix", "reference_id": 7 },
    { "type": "skill", "reference_id": 12 }
  ]
}

Response (extended):
{
  // Existing tick response fields...
  "session_gold": 1500.0,
  "cps_valid": true,

  // New discovery response (only if discoveries were sent):
  "new_ranks": [ { "entity_id": 42, "old_rank": "E", "new_rank": "C" } ],
  "new_discoveries": 3
}
```

The frontend accumulates encounter/kill data between ticks and flushes it with the next tick call. A standalone `POST /api/game/registry/unlock-batch` endpoint also exists for non-combat discoveries (e.g., idle training skill unlock, item acquisition from inventory).

### 3.7 Random Spawn Engine

**Spawn pool:** All entities in the `entities` table that have NO record in `entity_scene_appearances` AND no `first_scene_appeared` value.

```
Spawn check (per wave in Story Mode / per encounter in active Idle Training):
1. Roll random float [0, 1)
2. base_chance = game_configs["rare_spawn_base_chance"] (default: 0.005)
3. book_modifier = game_configs["rare_spawn_book_{book_number}_modifier"] (default: 1.0)
4. chapter_modifier = game_configs["rare_spawn_chapter_{chapter_number}_modifier"] (default: 1.0)
5. effective_chance = base_chance × book_modifier × chapter_modifier
6. If roll < effective_chance:
   - Select random entity from the rare pool
   - Replace one standard wave enemy with the rare spawn
   - Apply visual distinction (glow effect via PixiJS)
   - Track encounter in player_entity_discovery immediately
```

**Configurable values (`game_configs`):**
| Key | Default | Description |
| :--- | :--- | :--- |
| `rare_spawn_base_chance` | `0.005` | 0.5% base chance per wave |
| `rare_spawn_book_{N}_modifier` | `1.0` | Per-book multiplier |
| `rare_spawn_chapter_{N}_modifier` | `1.0` | Per-chapter multiplier |

## 5. Chat System

### 5.1 WebSocket Architecture

```
Client                          Server (FastAPI)
  |                                |
  |-- WS Connect /ws/chat ------->|  (JWT in query param)
  |                                |-- Validate JWT
  |                                |-- Add to connection_manager
  |<-- {"type":"history", ...} ----|  (last N messages from buffer)
  |                                |
  |-- {"type":"message", ...} ---->|  (send message)
  |                                |-- Profanity check
  |                                |-- Rate limit check
  |                                |-- Broadcast to all connections
  |<-- {"type":"message", ...} ----|  (receive broadcast)
  |                                |
  |-- {"type":"pong"} ------------>|  (heartbeat response)
  |<-- {"type":"ping"} -----------|  (every 30s)
```

**Connection Manager** (server-side singleton):
```python
class ConnectionManager:
    def __init__(self):

    async def broadcast(self, message, channel="global")
    async def send_personal(self, message, player_id)
```

### 5.3 Profanity Filter

**Implementation:** Aho-Corasick multi-pattern matcher loaded on server startup from `backend/profanity_blocklist.txt`.

```python
# On startup:
profanity_matcher = build_aho_corasick("backend/profanity_blocklist.txt")

# On message:
matches = profanity_matcher.find_all(message.content.lower())
if matches:
    for match_start, match_end in matches:
        message.content = message.content[:match_start] + "*****" + message.content[match_end:]
    # Message is delivered with censored content
```

- Uses `pyahocorasick` library for O(n) scanning regardless of blocklist size.
- Blocklist is a simple text file, one word/phrase per line.
- **Censoring behavior:** Matched words/phrases are replaced with a fixed `*****` (always 5 asterisks regardless of original word length) so the actual word cannot be inferred from the replacement length. The message is still delivered.

### 5.4 Rate Limiting

```python
class ChatRateLimiter:
    def __init__(self):
        self.timestamps: dict[int, deque] = {}  # player_id -> recent message timestamps

    def check(self, player_id: int, limit: int, window_s: int = 60) -> bool:
        now = time.time()
        q = self.timestamps.setdefault(player_id, deque())
        # Purge old timestamps
        while q and q[0] < now - window_s:
            q.popleft()
        if len(q) >= limit:
            return False  # rate limited
        q.append(now)
        return True
```

### 5.5 System Broadcasts — Rate Limiting

```python
class BroadcastRateLimiter:
    """Rate-limits system broadcasts shown to OTHER players.
    The achieving player always sees their own broadcast as a toast."""

    def __init__(self):
        self.recent_broadcasts: deque = deque()  # (timestamp, player_id)

    def should_broadcast(self, player_id: int, limit_per_minute: int) -> bool:
        now = time.time()
        # Purge old
        while self.recent_broadcasts and self.recent_broadcasts[0][0] < now - 60:
            self.recent_broadcasts.popleft()
        if len(self.recent_broadcasts) >= limit_per_minute:
            return False  # suppress chat broadcast, still send toast to achiever
        self.recent_broadcasts.append((now, player_id))
        return True
```

**Toast delivery:** The toast for the achieving player is sent via the existing REST response (e.g., `/complete` response includes achievement data) rather than WebSocket, so it's guaranteed delivery regardless of broadcast rate limiting.

### 5.7 Admin Chat Interface

Sections:

### 5.9 Cloud Run Deployment

**Single instance:** `--max-instances=1` to avoid multi-instance message sync issues. Sufficient for expected low traffic.

**WebSocket timeout:** Use Cloud Run's default 300s (5 min) request timeout. Client auto-reconnects with exponential backoff on disconnect. On reconnect, client receives the current in-memory buffer. The 5-minute cycle is invisible to users given low chat volume.

**No infrastructure changes needed** — WebSocket works natively on Cloud Run with the existing FastAPI setup.
