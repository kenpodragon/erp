# REC 3.3: The Elysium Emporium (Overworld Shop)

This document defines the complete requirements for the Elysium Emporium — the in-game store where players spend Elysium Shards on cosmetics, time-limited boosters, and curated bundles.

**Design:** [3.3_ELYSIUM_EMPORIUM_DESIGN.md](3.3_ELYSIUM_EMPORIUM_DESIGN.md) | **Schema:** [3.3_ELYSIUM_EMPORIUM_SCHEMA.md](3.3_ELYSIUM_EMPORIUM_SCHEMA.md)
**Parent:** [3.0_ECONOMY.md](3.0_ECONOMY.md) §3.3

---

## 1. Overview & Scope

### 1.1 Purpose
Section 3.3 introduces the first shard sink — a centralized in-game store called the **Elysium Emporium** — accessible from the Hub. Players spend Elysium Shards on:
- **Cosmetics:** Character skins (portrait + battle avatar + battle bar), chat flair, leaderboard badges, and lore-themed avatar profile pictures
- **Boosters:** Time-limited gameplay buffs (XP, Essence, Drop Rate) that stack multiplicatively with subscription boosts
- **Bundles:** One-time discounted packages mixing cosmetics and boosters

All shop items are **cosmetic or time-limited** — no permanent meta-upgrades, no pay-to-win.

### 1.2 Scope Boundaries
- **In Scope:** Shop catalog system, cosmetic purchase/equip flow, booster activation/timer/expiry, bundle system, featured/limited-time rotation, purchase confirmation, shard debit flow, active booster display, minimal admin CRUD for catalog management.
- **Out of Scope:** Cosmetic asset generation (deferred to `C_STORY_ASSET_GENERATORS.md` §8), gifting (not supported), player marketplace (3.5), full admin finance dashboard (3.6), donations (3.4).
- **Dependencies:** Shard balance & debit infrastructure (3.1), subscription boost stacking (3.2), Firebase Auth (1.0), Chat system flair rendering (2.6.4), Leaderboard badge rendering (2.7.3), Character visual_config system (2.4).

## 3. Character Skins

### 3.1 What a Skin Changes
A character skin is a visual set that modifies the player's appearance in three locations simultaneously:

| Display Point | What Changes | Technical Hook |
|:---|:---|:---|
| **Character Portrait** | Profile/hub portrait image | Player profile avatar rendering |
| **Battle Avatar** | PixiJS hero entity in CombatStage/BossStage | `visual_config` override on player character |
| **Battle Bar** | Hero portrait in the bottom battle bar | Battle bar hero portrait component |

### 3.2 Skin Types
Two categories of skins:

| Type | Count at Launch | Description | Availability |
|:---|:---|:---|:---|
| **Universal** | 2 | Usable by any class. Generic lore-themed skins. | Permanent catalog |
| **Class-Specific** | 4 (1 per class) | Tailored to Engineer, Conduit, Drifter, or Vessel. Only equippable by that class. | Permanent catalog |

**Total launch skins: 6** (2 universal + 4 class-specific).

### 3.3 Skin Equip Rules
- A player can own multiple skins but only **equip one at a time.**
- Equipping a skin changes portrait + battle avatar + battle bar simultaneously (it's a set).
- Unequipping reverts to the **base class default appearance** (from `character_classes.visual_config`).
- Class-specific skins are **only equippable by characters of that class.** Attempting to equip a wrong-class skin returns an error.
- If a player switches class (if ever supported), any equipped class-specific skin is automatically unequipped.

### 3.4 Skin Pricing

| Skin Type | Price (Shards) | ~USD Equivalent |
|:---|:---|:---|
| Universal Skin | 500 | ~$5.00 |
| Class-Specific Skin | 350 | ~$3.50 |

### 3.5 Skin Assets
Skin assets are pixel-art sprite sets generated by an automated tool (deferred to `C_STORY_ASSET_GENERATORS.md` §8). Each skin requires:
- Portrait image (128×128 px)
- Battle avatar sprite/color config (PixiJS-compatible)
- Battle bar portrait thumbnail (48×48 px)

Until the generator tool is built, placeholder assets (color palette swaps on existing PixiJS shapes) are used.

## 7. Booster System

### 7.1 Booster Types
Boosters are time-limited gameplay buffs purchased with Shards. Three boost types are available:

| Boost Type | Effect | Applied Where |
|:---|:---|:---|
| **XP Boost** | Multiplies all Character XP earned | Story Mode completion, Idle Training |
| **Essence Boost** | Multiplies all Elysium Essence earned | Story completion, Idle Training, achievements |
| **Drop Rate Boost** | Multiplies artifact drop chance rolls | Curated + generated artifact drops |

### 7.2 Duration & Magnitude Tiers
All values are admin-configurable via `game_configs`:

| Duration | XP Multiplier | Essence Multiplier | Drop Rate Multiplier | Price (Shards) | ~USD |
|:---|:---|:---|:---|:---|:---|
| 1 hour | 1.25x | 1.25x | 1.25x | 75 | ~$0.75 |
| 8 hours | 1.5x | 1.5x | 1.5x | 400 | ~$4.00 |
| 24 hours | 2.0x | 2.0x | 2.0x | 900 | ~$9.00 |

**9 booster items total** (3 types × 3 durations). The 8hr and 24hr tiers provide better value per hour, incentivizing larger purchases.

| Duration | Effective Hourly Cost (Shards) | Value vs 1hr |
|:---|:---|:---|
| 1 hour | 75/hr | baseline |
| 8 hours | 50/hr | 33% cheaper per hour |
| 24 hours | 37.5/hr | 50% cheaper per hour |

### 7.3 Booster Activation Rules
- **Immediate activation.** Boosters activate the moment they are purchased. There is no inventory/stockpile — the purchase IS the activation. The confirmation modal must clearly state: *"This booster activates immediately upon purchase."*
- **One active booster per type.** A player can have one XP booster, one Essence booster, and one Drop Rate booster active simultaneously, but NOT two XP boosters at once.
- **Overlap extends time.** If a player purchases a new booster of the same type while one is already active, the new duration is **added** to the remaining time. Example: 30 min remaining on a 1hr XP booster + buy another 1hr XP booster = 1hr 30min remaining at the same magnitude.
- **Magnitude on overlap:** When extending, the magnitude uses the **higher** of the two boosters. Example: 30 min remaining on a 1.25x XP booster + buy an 8hr 1.5x XP booster = 8hr 30min at 1.5x. When the extension period from the higher booster expires, the remaining time (if any from the lower booster) does NOT revert — it stays at the higher magnitude for simplicity.

### 7.4 Booster Timer Behavior
Booster timers tick differently based on boost type:

| Boost Type | Timer Ticks When | Rationale |
|:---|:---|:---|
| **XP Boost** | Player is in an active Story Mode session OR active Idle Training session | XP is only earned during gameplay |
| **Essence Boost** | Player is in an active Story Mode session OR active Idle Training session | Essence is only earned during gameplay |
| **Drop Rate Boost** | Player is in an active Story Mode session OR active Idle Training session | Drops only occur during gameplay |

**"Active session" means:**
- **Story Mode:** A `player_story_session` exists with `status = 'active'`. Timer ticks regardless of whether the browser tab is open or closed — the session is server-tracked.
- **Idle Training:** An active training session exists (training is inherently server-side). Timer ticks while training is running.
- **Hub browsing, being logged out, or any other state:** Timer does NOT tick.

The server calculates remaining time on each relevant request by subtracting elapsed active-session time since activation.

### 7.5 Booster Expiry
When a booster's timer reaches zero:
1. The boost multiplier is removed from the player's next calculation.
2. The active booster record is marked as `expired`.
3. The UI removes the booster from the active display.
4. No notification is sent (the countdown reaching 0 is the notification).

### 7.6 Booster Display
Active boosters are displayed in two locations:
- **Global Header (Story Mode):** Alongside existing subscription buff tray. Shows boost icon, magnitude, and countdown timer.
- **Hub Top Bar:** Compact booster indicators next to the shard balance. Shows active boost icons with remaining time on hover.

### 7.7 Stacking with Subscription Boosts
Shop boosters stack **multiplicatively** with subscription boosts (as defined in 3.2 §8.3):

```
total_multiplier = subscription_multiplier × shop_booster_multiplier
```

Examples:
- Subscriber (1.15x XP) + 1hr shop booster (1.25x XP) = **1.4375x XP**
- Subscriber with 6-month streak (1.25x XP) + 24hr shop booster (2.0x XP) = **2.5x XP**
- Non-subscriber (1.0x) + 8hr shop booster (1.5x XP) = **1.5x XP**

The `get_effective_multipliers(player_id)` function (new, extends 3.2's `get_subscriber_multipliers`) returns the combined multiplier for each boost type.

## 8. Bundle System

### 8.1 What Bundles Are
Bundles are curated packages containing a mix of cosmetics and/or boosters, sold at a discount compared to buying items individually.

### 8.2 Bundle Rules
- **One-time purchase only.** Each bundle can be bought once per player. The UI shows "Purchased" after buying.
- **Discounted.** Bundles are priced at **20% off** the sum of individual item prices (admin-configurable per bundle).
- **Mixed contents.** A bundle can contain any combination of cosmetics (skins, flair, badges, avatars) and boosters.
- **Partial ownership:** If a player already owns some items in a bundle, they can still buy it but receive only the items they don't own. The price is NOT adjusted — the player pays the full bundle price regardless. This must be clearly communicated in the UI: *"You already own X of Y items in this bundle."*
- **Booster in bundle:** If a bundle contains a booster, it activates immediately on purchase (same as standalone booster purchase).

## 9. Featured & Limited-Time Rotation

### 9.1 Featured Items
- An admin can mark any catalog item as **"Featured"** with a start and end date.
- Featured items appear in a prominent "Featured" section at the top of the Emporium.
- An item can exist in both the permanent catalog AND be featured simultaneously — featured is a spotlight, not a separate listing.
- Multiple items can be featured at the same time.

### 9.2 Limited-Time Exclusives
- An admin can create items with an **availability window** (start date → end date).
- Limited-time items are **only purchasable during their availability window.** Outside the window, they do not appear in the shop.
- Players who purchased a limited-time item **keep it permanently** — only the ability to purchase expires.
- Limited-time items display a countdown timer in the shop: *"Available for X days, Y hours."*

### 9.3 Admin Scheduling
- All featured/limited-time scheduling is done manually by admins via the catalog CRUD (minimal in 3.3, full UI in 3.6).
- No automated rotation system. Admins set explicit start/end dates per item.
- Items with `available_from = NULL` and `available_until = NULL` are permanently available.

## 10. Purchase Flow

### 10.1 Standard Purchase (Cosmetic)
1. Player browses the Emporium and selects an item.
2. **Confirmation modal** opens (reuses `PurchaseConfirmModal` pattern from 3.1):
   - Item name, description, icon/preview.
   - Price in Shards.
   - Current shard balance and balance after purchase.
   - "All sales are final." disclaimer.
   - [Confirm Purchase] / [Cancel] buttons.
3. On confirm: frontend calls `POST /api/shop/purchase` with `item_id`.
4. Backend validates:
   - Player is authenticated.
   - Item exists, is active, and is within availability window.
   - Player does not already own this item (for cosmetics) or bundle.
   - Player has sufficient shard balance (≥ 0 after debit).
   - For class-specific skins: player's active character matches the required class.
5. **Atomic transaction:**
   a. `debit_shards(player_id, price, source_type='shop_purchase', source_id=item_id)`
   b. Create `player_shop_item` ownership record.
   c. Log to `shard_transactions`.
6. Return success with updated balance and item details.

### 10.2 Booster Purchase
Same flow as §10.1 steps 1–4, with additional logic:
- Confirmation modal includes: *"This booster activates immediately upon purchase."*
- If a booster of the same type is already active, modal shows: *"You have an active [Type] booster with [X] remaining. Purchasing will extend it by [Duration]."*
- Step 5 includes:
   a. Debit shards.
   b. If no active booster of this type: create `player_active_booster` record with `activated_at = NOW()`, `duration_seconds`, `magnitude`.
   c. If active booster exists: add `duration_seconds` to remaining time, update magnitude to `MAX(current, new)`.
   d. Log to `shard_transactions`.

### 10.3 Bundle Purchase
Same flow as §10.1 steps 1–4, with:
- Modal shows all bundle contents with owned/new indicators.
- *"You already own X of Y items."* warning if applicable.
- Step 5 delivers each unowned item individually (cosmetics → ownership records, boosters → activation).
- Bundle purchase is logged as a single `shard_transactions` entry with `source_type = 'shop_purchase'` and `source_id = bundle_id`.

### 10.4 Insufficient Balance
- If the player's shard balance is less than the item price, the confirm button is disabled.
- A message displays: *"Not enough Shards. You need X more."* with a [Buy Shards] link that navigates to the "Buy Shards" tab.

### 10.5 All Sales Final
- **Players cannot self-service refund shop purchases.** All shard-to-item transactions are final.
- If a player contacts support, an admin can manually:
  1. Remove the item from the player's ownership (`player_shop_items` record).
  2. Credit shards back via `credit_shards()` with `source_type = 'admin_refund'`.
  3. Log the action in `shard_transactions`.
- This admin flow is handled via backend admin endpoints (minimal CRUD in 3.3, full UI in 3.6).

## 12. Boost Application (Server-Side)

### 12.1 Where Shop Boosters Apply

| System | How Boost Is Applied | Code Location |
|:---|:---|:---|
| Story Mode XP | Multiply XP at `/complete` by combined multiplier | `backend/routes/story_mode.py` |
| Idle Training XP | Multiply XP tick by combined multiplier | `backend/routes/game_training.py` |
| Essence (Story) | Multiply Essence at `/complete` by combined multiplier | `backend/routes/story_mode.py` |
| Essence (Idle) | Multiply Essence per level-up by combined multiplier | `backend/routes/game_training.py` |
| Essence (Achievement) | Multiply Essence reward by combined multiplier | `backend/services/achievement_service.py` |
| Artifact Drop Chance | Multiply drop chance threshold by combined multiplier | `backend/services/artifact_service.py` |

### 12.2 Combined Multiplier Resolution
A new utility function `get_effective_multipliers(player_id)` combines subscription and shop booster multipliers:

```python
def get_effective_multipliers(player_id: int) -> dict:
    sub = get_subscriber_multipliers(player_id)
    shop = get_active_shop_boosters(player_id)  # returns {type: magnitude} for active boosters
    return {
        "xp": sub["xp"] * shop.get("xp", 1.0),
        "essence": sub["essence"] * shop.get("essence", 1.0),
        "drop_rate": sub["drop_rate"] * shop.get("drop_rate", 1.0),
        "training_speed": sub["training_speed"],  # no shop booster for training speed
        "active_boosters": [...]  # list of active boosters with remaining time
    }
```

All game systems that currently call `get_subscriber_multipliers()` will be updated to call `get_effective_multipliers()` instead.

### 12.3 Booster Timer Calculation (Server-Side)
The server tracks booster time using active session durations, not wall-clock time:

```
remaining_seconds = total_duration_seconds - elapsed_active_session_seconds
```

Where `elapsed_active_session_seconds` is calculated by summing:
- Time spent in active Story Mode sessions since booster activation
- Time spent in active Idle Training sessions since booster activation

This is computed on-demand each time the booster status is queried (lazy evaluation).

### 13.2 Admin Refund Flow
When a support ticket requests a shop item refund:
1. Admin calls `POST /api/admin/shop/player/{player_id}/refund` with `{ item_id, reason }`.
2. Backend:
   a. Removes the `player_shop_item` ownership record (or marks it `refunded`).
   b. If item is currently equipped, unequips it first.
   c. Credits shards back: `credit_shards(player_id, original_price, 'admin_refund', item_id)`.
   d. Logs to `shard_transactions` with `source_type = 'admin_refund'`.
   e. Logs admin action to `activity_events`.
3. For boosters: if the booster is still active, the remaining time is forfeited. Shards are still refunded at full price.

## 14. Error Handling & Edge Cases

### 14.1 Insufficient Balance
- Purchase endpoint returns 400: "Insufficient shard balance."
- Frontend disables the buy button and shows deficit amount.

### 14.2 Already Owned
- Cosmetic purchase endpoint returns 400: "You already own this item."
- Bundle purchase is allowed even with partial ownership (see §8.2).

### 14.3 Class Mismatch
- Attempting to purchase a class-specific skin for the wrong class returns 400: "This skin requires the [ClassName] class."
- Attempting to equip a wrong-class skin returns 400 (defensive — should not be reachable in UI).

### 14.4 Item Not Available
- Purchasing an item outside its availability window returns 400: "This item is no longer available."
- Purchasing a deactivated item returns 404.

### 14.5 Concurrent Purchases
- Atomic shard debit with row-level locking prevents double-spend on rapid clicks.
- Each purchase generates a unique `shard_transactions` entry — no idempotency key needed (unlike Stripe where webhooks retry).

### 14.6 Negative Shard Balance
- Players with a negative shard balance (from refunds/disputes in 3.1) cannot purchase any shop items.
- The entire Emporium shows a banner: *"Your shard balance is negative. Please purchase more shards to continue shopping."*

### 14.7 Booster During No Active Session
- If a player buys a booster while not in Story Mode or Idle Training, the booster is activated but the timer does not tick until they enter a session.
- The confirmation modal notes: *"Timer begins when you enter Story Mode or Idle Training."*

### 14.8 Bundle with Active Booster Conflict
- If a bundle contains a booster and the player already has that boost type active, the booster extends the active timer (same as standalone booster overlap rules in §7.3).

## 15. Security Requirements

### 15.1 API Authentication
- All `/api/shop/*` endpoints require Firebase JWT authentication.
- Players can only purchase items for themselves.
- Owned items are scoped to the authenticated player.

### 15.2 Server-Side Validation
- All prices, availability checks, class restrictions, and balance checks are performed server-side.
- The client displays prices but the server is the source of truth.
- Booster magnitudes and durations come from the database — the client cannot specify custom values.

### 15.3 Rate Limiting
- `POST /api/shop/purchase`: Max 10 requests per player per minute.
- `GET /api/shop/catalog`: Max 30 requests per player per minute.

### 15.4 Admin Endpoints
- All `/api/admin/shop/*` endpoints require admin JWT auth (separate from player auth).
- Admin actions are logged to `activity_events` with the admin's player_id.
