# REC 2.6: Economy, Anti-Cheat & Discovery

This document defines the server-authoritative validation mechanisms, social communication, discovery/collection systems, new player onboarding, UI polish, and accessibility features for the Elysium Rising MMORPG.

**Implementation Order:** Animation Toggle (2.6.0) > Anti-Cheat (2.6.1) > Discovery System (2.6.2) > Onboarding & UI Polish (2.6.3) > Chat System (2.6.4)

---

## 1. Advanced Anti-Cheat & Validation

### 1.1 Existing Server-Authoritative Systems (Already Implemented)
The following validation is already in place and forms the foundation for 2.6 hardening:
- **CPS Rate Limiting:** Server enforces `click_rate_cap` (default 20 CPS) via `game_configs`. Excess clicks are silently clamped to `cps_cap x elapsed_s`. Returns `cps_valid: false` to client.
- **Gold Verification:** Server recalculates expected gold from `_calc_zone_gold(zone) x waves_completed_delta`. If client reports gold > 20x expected, corrects down to 5x expected. Returns `gold_corrected: true`.
- **Server-Authoritative State:** All gold, zone, and wave state stored server-side on `PlayerStorySession`. Client cannot claim arbitrary gold.
- **Upgrade Cost Verification:** Upgrades purchased through server endpoint that recalculates costs.
- **Essence Conversion:** Calculated server-side at `/complete` based on server-held `session_gold`.

### 1.2 New: Wave Completion Validation
- [x] **DPS-Based Wave Plausibility:** The `/tick` endpoint must validate `waves_completed_delta` against the player's theoretical maximum DPS (click damage + auto DPS + active skill contributions) and elapsed time.
- [x] **Max Waves Per Tick:** Calculate the maximum number of waves a player could plausibly complete given their current DPS, zone HP scaling, and `elapsed_ms`. If `waves_completed_delta` exceeds this, clamp to the plausible maximum.
- [x] **Configurable Tolerance:** A `wave_validation_tolerance` multiplier in `game_configs` (e.g., 2.0x) to allow for burst damage, critical hits, and skill combos without false positives.

### 1.3 New: Session Integrity Check at Completion
- [x] **Final Sanity Check:** At `/complete`, verify that total `session_gold` is plausible given:
  - Session duration (`created_at` to `now`)
  - Highest zone reached
  - Player's DPS capability (permanent stats + session upgrades)
- [x] **Correction:** If total gold exceeds plausible maximum by a configurable threshold (`session_gold_tolerance` in `game_configs`), correct down to the plausible maximum.
- [x] **Anomaly Logging:** Log the correction as an anomaly event (see 1.4).

### 1.4 New: Anomaly Logging & Behavioral Flagging
- [x] **Activity Event Logging:** All significant anomalies are logged to `activity_events` with event type `anti_cheat_anomaly`. Logged anomalies include:
  - CPS violations (when `cps_valid: false`)
  - Gold corrections (when `gold_corrected: true`)
  - Wave completion implausibility (when waves are clamped)
  - Session integrity corrections at `/complete`
  - Perfectly uniform click intervals (pattern detection)
- [x] **Event Payload:** Each anomaly log includes: `player_id`, `session_id`, anomaly type, reported value, corrected value, and timestamp.
- [x] **Admin Visibility:** Anomaly events are filterable in the existing admin activity log viewer.
- [x] **No Auto-Tickets:** No automatic support ticket creation. Admins review anomaly patterns manually via activity log filters.

### 1.5 New: Client-Side CPS Feedback (Two-Tier)
- [x] **Tier 1 — Immediate Visual Cue:** When a `/tick` response returns `cps_valid: false`, the `GoldOdometer` component flashes red briefly to indicate the correction.
- [x] **Tier 2 — Escalated Warning Toast:** If CPS violations persist for a configurable duration (`cps_warning_threshold_seconds` in `game_configs`), display a non-blocking toast/banner: *"Excessive automated clicking detected. Max {CPS_CAP} CPS is recorded."* The toast does not interrupt gameplay — it is informational only.
- [x] **Reset:** The violation timer resets when the player returns to valid CPS for a configurable cool-down period.

## 2. Social & Communication

### 2.1 Integrated Chat (WebSocket)
- [x] **Technology:** FastAPI native WebSocket endpoint. Minimal infrastructure, no external dependencies (no Redis, no message broker).
- [x] **Global Channel:** A single global chat channel available to all authenticated players.
- [x] **Multi-Channel Schema:** Data model supports multiple channels from day one (channel ID/name/type fields) so chapter-specific or topic channels can be enabled later without migration. Only the global channel is active in 2.6.
- [x] **In-Memory Storage:** Chat messages are held in a rolling in-memory buffer (configurable size via `game_configs`, e.g., `chat_buffer_size: 200`). Messages are lost on server restart. No database persistence for chat history.
- [x] **Identity:** Each message displays: `[ClassIcon] CharName [Level]`. Level = Character Level (permanent).
- [x] **Authentication:** WebSocket connections require a valid Firebase JWT. Unauthenticated connections are rejected.
- [x] **Reconnection:** Client auto-reconnects on disconnect with exponential backoff. On reconnect, receives the current in-memory buffer (last X messages).

### 2.2 Moderation
- [x] **Profanity Filter:** Server-side Aho-Corasick filtering against `backend/profanity_blocklist.txt`. Filtered content replaced with `*****`.
- [x] **Spam Control:** Configurable message-per-minute rate limit per player (`chat_rate_limit_per_minute` in `game_configs`).
- [x] **Admin Mute/Ban:** Ability to mute a player from chat (temporary or permanent) via the admin panel. Muted players can still read but not send messages.

### 2.3 System Broadcasts & Notifications
- [x] **Milestone Broadcasts:** The "System" account broadcasts major achievements to the global channel:
  - Chapter/Book completions
  - Finding super-rare items (rarity threshold set in `game_configs`, e.g., `broadcast_rarity_min`)
  - First-time boss defeats
- [x] **Toast Notifications:** The player who triggered the achievement always sees a toast notification, regardless of rate limiting.
- [x] **Broadcast Rate Limiting:** Other players' achievement broadcasts are rate-limited (configurable via `game_configs`, e.g., `broadcast_rate_limit_per_minute`) to prevent spam during high-activity periods. A player always sees their own achievements.

### 2.4 Admin Chat Interface
- [x] **Channel Management:** Admin page to create, rename, enable/disable chat channels. Global channel cannot be deleted.
- [x] **Chat Monitor:** Read-only view of live chat for moderation purposes.
- [x] **Player Mute Controls:** Mute/unmute players from the admin chat interface.

## 3. The Akashic Records (Discovery System)

**Location:** Integrated into the Home Base Hub (builds on existing 2.7 framework).

### 3.1 The Etheric Registry (Monster Codex)

#### 3.1.1 Two-Level Tracking
- [x] **Per-Variant Tracking:** Track `encountered` and `killed` counts for each individual entity record in the database (e.g., "Shadow Wraith", "Frost Wraith", "Ancient Wraith" are separate entries).
- [x] **Per-Type Aggregation:** Roll-up view by entity type/category showing totals across all variants (e.g., "Wraiths: 8/40 variants discovered, 100 total kills — 70 Shadow Wraith, 30 Frost Wraith").
- [x] **New DB Table:** `player_entity_discovery` — tracks per-player, per-entity encounter and kill counts, rank, and first-seen timestamp.

#### 3.1.2 State-Based Visibility
- [x] **Ether Mist (Future):** Entities in chapters the player hasn't reached are completely hidden (no name, no count, just "Mist").
- [x] **Grey Lines (Current/Passed):** Entities in current or passed chapters that haven't been encountered are shown as blurred grey silhouettes. They count toward the chapter total (e.g., "15/45 encountered").
- [x] **Revealed:** Entities encountered at least once in Story Mode, Idle Training active combat, or as a random spawn.

#### 3.1.3 Ranked Reveal System (E -> SS)
- [x] **Rank-Up by Kills:** Progression through ranks requires kill count thresholds.
- [x] **Configurable Thresholds:** Kill counts for each rank are set in `game_configs` (e.g., `codex_rank_e: 1`, `codex_rank_c: 25`, `codex_rank_a: 100`, `codex_rank_ss: 500`).
- [x] **Rank Rewards (Progressive Reveal):**
  - **Rank E (1 Kill):** Name, image, and basic lore unlocked.
  - **Rank C:** Base HP and gold drops revealed.
  - **Rank A:** Full stat block (Atk, Def, etc.) revealed.
  - **Rank SS:** Hidden lore secrets and 100% completion badge.
- [x] **Fallback Logic:** Missing lore/stats trigger a generic placeholder and log to `dev_content_audit`.

### 3.2 Skill & Item Library
- [x] **Unlock Trigger — Skills:** Discovered when first purchased in a Story Mode session OR first trained via Idle Training (whichever happens first).
- [x] **Unlock Trigger — Items:** Discovered when first owned (acquired as loot, equipped, or purchased from a shop). Merely viewing an item in a shop does not unlock it.
- [x] **UI Feedback:** "New" badge on undiscovered entries. Badge clears on hover.
- [x] **Content:** Full mechanical breakdown and narrative origin for each entry.

### 3.3 Discovery Counters
- [x] **Hub Display:** Show discovery progress on the Home Base Hub (e.g., "12/99 skills unlocked", "45/200 entities discovered").
- [x] **Per-Category Counters:** Separate counters for entities, skills, items, and lore entries.

### 3.4 Random Spawns (Rare Entities)
- [x] **Spawn Pool:** Entities in the database that are NOT associated with any scene (no `entity_scene_appearances` record or no `first_scene_appeared` value) form the rare spawn pool.
- [x] **Universal Availability:** Rare spawns can appear anywhere — Story Mode combat, Idle Training active clicking — regardless of player progression. A brand-new player in Book 1 Chapter 1 could (rarely) encounter one.
- [x] **Spawn Rate Configuration:** Configurable in `game_configs`:
  - `rare_spawn_base_chance`: Base probability per wave/encounter (e.g., 0.005 = 0.5%)
  - `rare_spawn_per_book_modifier`: Optional per-book multiplier (e.g., later books have slightly higher rare spawn rates)
  - `rare_spawn_per_chapter_modifier`: Optional per-chapter multiplier
- [x] **Visual Distinction:** Rare spawns have a distinct visual indicator (glow, border, or particle effect) so the player knows they've found something special.
- [x] **Discovery Integration:** Killing a rare spawn immediately registers it in the Etheric Registry.

### 3.5 Static Gameplay WIKI (Help Pages)
- [x] **Frontend Static Pages:** "How to Play" guides explaining gameplay mechanics: stats, combat, idle training, beneficial effects, currencies, etc.
- [x] **Contextual Help Icons:** Small "?" icons throughout the UI (on stat labels, skill descriptions, upgrade panels) linking directly to the relevant static help page.
- [x] **Separate from Akashic Records:** These are static reference pages, not the dynamic discovery system.

## 4. New Player Onboarding & UI

### 4.1 Welcome & Changelog Modal
- [x] **Combined Modal:** A single modal shown on login that serves two purposes:
  - **Changelog / What's New:** Top section shows recent updates and patch notes (content managed via admin or static file).
  - **Tutorial Link:** Bottom section with "New Player / Need Help? Click here for a tutorial/overview" link.
- [x] **Changelog Versioning:** Track the last-seen changelog version in `player.settings` so the modal only auto-shows when there's something new. Can be dismissed and reopened from a help menu.

### 4.2 Interactive Tutorial
- [x] **Scope:** Account-wide, tracked via `player.settings.has_completed_onboarding`.
- [x] **User Control:** Skippable (even on first run) and replayable at any time from settings/help menu.
- [x] **No Rewards:** Tutorial does not grant items, gold, levels, or any gameplay advantage. Every player starts "naked and alone" in Book 1, Chapter 1, Scene 1.
- [x] **Content:** Hybrid flow — narrative slides + interactive coach marks explaining:
  - Hub navigation (map, inventory, skills, home base)
  - Story Mode combat basics (clicking, skills, upgrades)
  - Idle Training overview
  - Discovery system / Akashic Records
- [x] **Non-Blocking:** Tutorial overlays do not prevent the player from interacting with the game underneath.

### 4.3 Aesthetic Polish Pass ("Magic Research 2" Standard)
- [x] **Hub & Story Mode:** Apply consistent visual polish:
  - Rounded corners on panels, buttons, and modals
  - Box shadows and subtle depth
  - Consistent iconography (use icon library or custom SVGs)
  - Uniform spacing, padding, and typography scale
  - High-contrast dark theme refinement
  - Hover/active/focus states on all interactive elements
  - Smooth transitions on state changes
- [x] **Concrete Checklist:** Define a specific list of components/pages to polish during the design phase.
- [x] **Cyberpunk Terminal Exception:** Idle Training (Loop C) retains the green-on-black retro terminal aesthetic. No "Magic Research 2" styling applied there.

### 4.4 Animation Toggle (Reduce Motion)
- [x] **Settings Toggle:** Add a "Reduce Motion" toggle to the Game Settings modal (`TopBar.tsx`).
- [x] **Battle Banner:** When enabled, hide `BottomAnimatedBanner` entirely (or replace with a static image).
- [x] **Combat Animations:** Reduce or disable non-essential VFX (floating damage numbers, coin particles, screen shake, skill effects).
- [x] **Persistence:** Store preference in `player.settings` JSONB column (key: `reduce_motion`), synced via `PATCH /api/players/me/settings`.
- [x] **CSS Integration:** Apply `prefers-reduced-motion` media query as baseline; toggle overrides for users who want motion on despite OS setting.
