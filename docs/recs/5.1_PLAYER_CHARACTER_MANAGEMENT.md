## 1. Overview & Scope

### 1.1 Purpose
Section 5.1 transforms the existing PlayerDetail admin page into a full **support and testing workbench**. Today, admins can view player profiles, ban/unban, force logout, edit aliases, toggle permissions, and manage shards via the Finance Dashboard. However, there is **no ability to directly edit characters, items, currency (Essence), skills, or progression** — all of which are critical for:

- **Player support:** Resolving issues where a player's state is corrupted or incorrect (e.g., lost items, wrong progression, stuck on a scene).
- **QA/Testing:** Creating specific game states to test features (e.g., setting a character to level 50, granting specific items, unlocking late-game content).
- **Moderation:** Investigating suspicious player states by viewing detailed activity timelines.

After this phase, an admin should be able to fully manage any player's game state without touching the database directly.

### 1.2 Scope Boundaries
- **In Scope:** Character stat/level/XP editing, class reassignment with skill mapping, item crafting tool (manual + random modes), existing item component editing with stat recalculation, Essence currency grant/debit with audit trail, progression editor (book/chapter/scene unlocking with backfill), boss completion reset, idle training skill level editing, activity timeline viewer.
- **Out of Scope:** Shard management (already in Finance Dashboard 3.6), subscription/premium override (already in Finance Dashboard 3.6), multi-character support (future phase), bulk operations across multiple players (future phase), session gold manipulation (temporary per-session), session upgrade editing (temporary per-session).
- **Dependencies:** All prior phases (1.0–3.6, 5.7) complete. Database migrations 001–055 applied. Existing PlayerDetail page and admin route infrastructure.

### 1.3 Existing Foundation

| Component | Source | Current Capability |
|:---|:---|:---|
| `PlayerDetail.tsx` | 1.0 / 3.6 | View profile, ban/unban, force logout, edit alias, toggle permissions, finance widget |

### 1.4 UI Model
All editing tools are launched as **separate modal dialogs** from the PlayerDetail page. The PlayerDetail page gains new action buttons that open these modals. Each modal is self-contained with its own load/save/cancel workflow.

### 1.5 Audit Requirements
Every admin action in this phase **must** be logged to `admin_audit_log` with:
- `admin_email`: Authenticated admin's email
- `action`: Descriptive action name (e.g., `character_stat_edited`, `item_crafted`, `essence_granted`)
- `target_type`: `player` or `character`
- `target_id`: Player or character ID
- `details`: JSON payload with before/after values where applicable
- `ip_address`: Request IP

Additionally, Essence adjustments create records in a dedicated `admin_essence_adjustments` table (following the `admin_shard_adjustments` pattern from 3.6).

## 2. Character Deep Editor

### 2.1 Purpose
Allow admins to directly edit a player's character attributes that persist through normal gameplay. This is the primary tool for fixing corrupted character state or setting up test scenarios.

### 2.2 Editable Fields

The following fields on `player_characters` are directly editable:

| Field | Type | Constraints | Notes |
|:---|:---|:---|:---|
| `character_name` | string | 3–20 chars, profanity check | Same validation as player-facing creation |
| `level` | integer | 1–999 | Setting level does NOT auto-adjust XP |
| `character_xp` | float | >= 0 | Setting XP does NOT auto-adjust level |
| `class_id` | integer | Must reference valid `CharacterClass` | Triggers class reassignment flow (§2.3) |

**Not directly editable:** `strength`, `agility`, `intelligence` — these are computed fields populated by `recalculate_character_stats()`. The admin edits the *sources* (level, equipment, skills, class) and the stats recompute automatically.

### 2.3 Class Reassignment Flow

When an admin changes a character's `class_id`:

1. **Identify skill categories:**
   - **Universal skills:** Skills not flagged as class-exclusive (available to all classes).
   - **Old class-exclusive skills:** Skills exclusive to the *current* class.
   - **New class-exclusive skills:** Skills exclusive to the *target* class.

2. **Skill mapping:**
   - Universal skills retain their current `CharacterSkillLevel` (level, XP, training state) unchanged.
   - Old class-exclusive skills are mapped to new class-exclusive skills **by ID order** (1st old → 1st new, 2nd old → 2nd new, etc.). The mapped skill inherits the level and XP from the old skill. (Note: `Skill` model has no `sort_order` field; `id` order = creation order.)
   - If the new class has **fewer** exclusive skills than the old, excess old skill levels are lost (logged in audit).
   - If the new class has **more** exclusive skills than the old, extra new skills start at level 1.

3. **Post-reassignment:**
   - `recalculate_character_stats()` is called to recompute all stats with new class affinities.
   - Audit log records: old class, new class, full skill mapping (old_skill_id → new_skill_id, level transferred).

4. **Equipment check (warning only):**
   - If any equipped items have `stat_requirements` that the character no longer meets after class change, a **warning** is shown to the admin (items remain equipped but may not function correctly in gameplay until requirements are met again).

### 2.4 UI: Character Deep Editor Modal

- **Trigger:** "Edit Character" button on each character card in PlayerDetail.
- **Layout:** Form with current values pre-populated, edit fields alongside.
- **Sections:**
  - Character Info: name, level, XP
  - Class: dropdown of all `CharacterClass` options, with current class highlighted. Changing class shows a confirmation dialog explaining the skill mapping before applying.
  - Current Stats (read-only): Display current computed STR/AGI/INT with source breakdown (class base + idle bonus + lore + level + equipment + artifacts) so the admin understands what's driving each stat.
- **Actions:** Save (validates + applies + recalculates stats), Cancel.
- **Feedback:** Success toast with summary of changes. Error toast on validation failure.

## 3. Item Crafting Tool

### 3.1 Purpose
Allow admins to create items and grant them to a player's inventory, OR edit components on existing items to recalculate stats. This piggybacks on the existing `item_generator.py` component system.

### 3.2 Item Creation — Two Modes

#### 3.2.1 Manual Mode (Full Control)
Admin selects every component:

| Component | Source Table | Selection |
|:---|:---|:---|
| Gear Slot | `gear_slots` | Dropdown |
| Item Type Base | `item_type_bases` | Dropdown (filtered by selected gear slot) |
| Prefix | `item_prefixes` | Dropdown |
| Quality | `item_qualities` | Dropdown |
| Lore Tag | `item_lore_tags` | Dropdown |
| Suffix | `item_suffixes` | Dropdown |
| Rarity | enum | Dropdown: common / uncommon / rare / epic / cosmic |

After selection, the system calculates stats using the same formula as `generate_dream_item()`:
- Base stats: admin selects a value within the `item_type_base.base_stat_range` (min–max slider per stat)
- Prefix stat bonuses applied
- Suffix stat bonuses applied
- Rarity multiplier applied: `{common: 1.0, uncommon: 1.3, rare: 1.7, epic: 2.2, cosmic: 3.0}`

**Live preview:** Stats update in real-time as components are selected, so the admin can see the effect before granting.

**Item level:** Admin sets manually (default: character's current level).

#### 3.2.2 Random Mode (Quick Generate)
Admin optionally constrains:
- Gear slot (optional — random if not selected)
- Rarity (optional — random if not selected, weighted by book 1 defaults)

All other components are randomly selected (same logic as `generate_dream_item()`). Preview shown before granting.

### 3.3 Granting Items
- Item is created as an `InventoryItem` with `acquired_from = "admin_grant"`.
- A `PlayerInventory` record is created with `is_equipped = false` (placed in bag).
- **Bag capacity check:** If player's bag is full (10 slots), the admin is warned and can choose to grant anyway (exceeding the soft cap) or cancel.
- Audit log records: item details, target character, admin who granted.

### 3.4 Existing Item Editor
Accessible from the player's inventory view within the Character Deep Editor context:

- **Editable components:** Prefix, Quality, Lore Tag, Suffix, Rarity. Changing any of these triggers stat recalculation using the same formula.
- **Item Type Base and Gear Slot** are NOT editable (changing these would fundamentally alter the item identity and slot).
- **Live preview:** Shows current stats vs. new calculated stats side-by-side as components are changed.
- **Save:** Updates the `InventoryItem` record, recalculates stats, triggers `recalculate_character_stats()` if item is equipped.
- **Audit log:** Records before/after for each changed component and resulting stat changes.

### 3.5 Artifact Editing
The Item Editor also supports editing `PlayerArtifact` records:

- **Generated artifacts:** Editable components: `artifact_prefix`, `artifact_suffix`, `rarity`. Changing any triggers stat_bonus recalculation following the same formula as `generate_artifact()`.
- **Curated artifacts:** Editable: `rarity` tier (changes which `CuratedArtifactTier` row applies, updating stat_bonuses and unique_effect_text accordingly).
- **Type base** is NOT editable for either artifact type.
- **Live preview:** Shows current stat bonuses vs. new calculated bonuses side-by-side.
- **Save:** Updates `PlayerArtifact`, triggers `recalculate_character_stats()`.
- **Audit log:** Records before/after for each changed component and resulting stat bonus changes.

### 3.6 UI: Item Crafting Modal

- **Trigger:** "Craft Item" button in PlayerDetail (per character).
- **Layout:** Split view — component selectors on left, live stat preview on right.
- **Mode toggle:** "Manual" / "Random" tabs at top.
- **Grant button:** Disabled until all required components are selected (manual) or generated (random). Shows confirmation with full item card preview.

### 3.7 UI: Item Editor Modal

- **Trigger:** Click on any item in the character's inventory display.
- **Layout:** Current item card + editable component dropdowns + before/after stat comparison.
- **Actions:** Save changes, Discard (delete item from inventory with confirmation), Cancel.

## 4. Currency Editor (Essence)

### 4.1 Purpose
Allow admins to grant or debit Elysium Essence to/from a player's character, with a mandatory reason field and full audit trail. This covers the per-character `PlayerEssence.current_balance` and the account-wide `PlayerMetaProgression.elysium_essence`.

### 4.2 Adjustment Flow

1. Admin selects the target character (if player has one).
2. Admin enters:
   - **Amount:** Positive number (grant or debit). Essence uses float precision to match `PlayerEssence.current_balance`.
   - **Direction:** Grant (+) or Debit (−).
   - **Reason:** Free-text, required (min 10 chars). Examples: "Compensation for lost progress", "QA testing", "Abuse correction".
3. System updates:
   - `PlayerEssence.current_balance` += amount (or -= for debit).
   - `PlayerMetaProgression.elysium_essence` += amount (for grants only; debits reduce `spent_essence`).
   - `PlayerMetaProgression.total_essence_earned` += amount (for grants only).
4. Creates `AdminEssenceAdjustment` record (see Schema doc).
5. Logs to `admin_audit_log`.

### 4.3 Balance Protection
- Debit cannot reduce `PlayerEssence.current_balance` below 0. If the requested debit exceeds the current balance, the admin is warned and can choose to debit only the available balance or cancel.
- Note: All essence values are `float` (matching `PlayerEssence.current_balance`, `PlayerMetaProgression.elysium_essence`).
- Current balance is displayed prominently before and after preview.

### 4.4 UI: Essence Adjustment Modal

- **Trigger:** "Adjust Essence" button in PlayerDetail (per character).
- **Layout:** Current balance display, grant/debit toggle, amount input, reason textarea, before/after preview.
- **Confirmation:** Double-confirm for large adjustments (> 10,000 Essence, configurable).
- **History:** Scrollable list of recent admin adjustments for this character (last 10).

## 5. Progression Editor

### 5.1 Purpose
Allow admins to manually set a player's story progression — unlocking or resetting book/chapter/scene progress. Critical for QA (jumping to late-game content) and support (fixing stuck progression).

### 5.2 Progression Unlocking (Forward Jump)

When an admin sets progression to a target book/chapter/scene:

1. **Backfill all prior content:**
   - For every scene before the target: create a `PlayerSceneRecord` with `first_completed_at = now`, `best_wave = 1`, `best_time_seconds = 0`, `total_runs = 1` if no record exists. Existing records are preserved.
   - For every boss scene before the target: create a `boss_completions` record if none exists (first-clear rewards are NOT granted — only the completion flag).
2. **Update `PlayerProgress`:** Set `book_number`, `chapter_number`, `scene_number` to the target.
3. **Audit log:** Records old progression position and new target.

### 5.3 Progression Reset (Backward Jump)

When an admin sets progression backward:

1. **Update `PlayerProgress`:** Set to the target position.
2. **Scene records are NOT deleted** — personal bests and completion data are preserved. The player simply replays from the new position.
3. **Admin receives a warning** that scene records still exist and the player will see those scenes as "completed" on the map.

### 5.4 Boss Completion Reset

- Admin can reset individual boss completions for a character.
- **Deletes** the `boss_completions` row, allowing the player to earn first-clear rewards again on next defeat.
- Displays a list of all completed bosses with scene name, chapter, and completion date.
- Single-select or multi-select reset with confirmation.
- Audit log records each reset.

### 5.5 UI: Progression Editor Modal

- **Trigger:** "Edit Progression" button in PlayerDetail (per character).
- **Layout:**
  - **Current Position:** Displays current book/chapter/scene with breadcrumb.
  - **Target Selector:** Three cascading dropdowns — Book → Chapter → Scene. Selecting a book filters chapters; selecting a chapter filters scenes.
  - **Direction indicator:** Shows "Advancing (will backfill X scenes)" or "Rewinding (records preserved)" based on target vs. current.
  - **Boss Completions Section:** Table of completed bosses with checkboxes for reset.
- **Actions:** Apply progression change, Reset selected bosses, Cancel.
- **Confirmation:** Required for both forward and backward jumps, with clear explanation of what will happen.

## 6. Skill Editor (Idle Training Levels)

### 6.1 Purpose
Allow admins to edit `CharacterSkillLevel` records — the idle training levels that determine base power floor in Story Mode. This does NOT bypass skill prerequisites.

### 6.2 Editing Rules

- Admin can set the `level` and `current_xp` for any skill the character has a `CharacterSkillLevel` record for.
- **Prerequisite enforcement:** If a skill has unmet prerequisites (checked via `evaluate_prerequisites()`), the skill row is displayed but **grayed out** with a tooltip showing which prerequisites are missing. The admin can then use the same editor to set the prerequisite skill levels first.
- **New skill records:** If a character doesn't have a `CharacterSkillLevel` for a skill (hasn't trained it yet), the admin can create one — but only if prerequisites are met.
- After any edit, `recalculate_character_stats()` is called to update stat contributions from idle training.
- Audit log records: skill_id, old_level, new_level, old_xp, new_xp.

### 6.3 UI: Skill Editor Modal

- **Trigger:** "Edit Skills" button in PlayerDetail (per character).
- **Layout:** Table of all skills with columns:
  - Skill Name | Category | Current Level | New Level (editable) | Current XP | New XP (editable) | Prerequisites (status indicators)
- **Visual cues:**
  - Green checkmark on skills with all prerequisites met.
  - Red lock icon on skills with unmet prerequisites, with tooltip listing what's needed.
  - Yellow warning on skills where changing the level would affect dependent skills' prerequisite status.
- **Bulk actions:** "Reset All to Level 1" button with confirmation.
- **Actions:** Save all changes, Cancel.

## 7. Activity Timeline

### 7.1 Purpose
Provide a unified, chronological view of a player's recent activity across all game systems. Essential for investigating support tickets, suspicious behavior, and understanding player state.

### 7.2 Data Sources

The timeline aggregates events from:

| Source | Event Types | Table |
|:---|:---|:---|
| **Activity Events** | player_login, player_logout, character_created, profile_updated | `activity_events` |
| **Story Sessions** | Session start, session complete, deaths | `player_story_sessions` |
| **Achievements** | Achievement unlocked | `player_achievements` |
| **Anti-Cheat** | Anti-cheat anomaly flags | `activity_events` (type = `anti_cheat_anomaly`) |
| **Inventory** | Item acquired, item equipped, item discarded | `activity_events` |
| **Admin Actions** | Ban, unban, edit, shard adjustment, essence adjustment | `admin_audit_log` (filtered to this player) |
| **Support Tickets** | Ticket created, status changes | `support_tickets` |
| **Purchases** | Shard purchases, subscription changes, shop purchases, donations | `payment_orders`, `shard_transactions` |

### 7.3 Timeline Display

- **Default range:** Last 7 days.
- **Pagination:** "Load more" button to go further back in 7-day increments.
- **Filtering:** Filter by event category (checkboxes): Gameplay, Economy, Admin, Social, Anti-Cheat.
- **Event cards:** Each event displays:
  - Timestamp (relative + absolute on hover)
  - Event type icon + label
  - Brief description (e.g., "Completed Scene 'The Dark Descent' — 42 waves, 1,250 gold")
  - Expandable detail section for events with JSON payloads

### 7.4 Anti-Cheat Highlighting
Events of type `anti_cheat_anomaly` are visually highlighted with a red border and warning icon. The detail section shows the full anomaly data (CPS readings, validation failures, etc.).

### 7.5 UI: Activity Timeline Modal

- **Trigger:** "Activity Timeline" button in PlayerDetail.
- **Layout:** Vertical timeline (newest first) with category filter checkboxes at top, date range indicator, and "Load more" at bottom.
- **Size:** Large modal (80% viewport width, 90% height) to accommodate timeline content.

## 11. Design Decisions (Resolved)

| # | Decision | Resolution | Rationale |
|:---|:---|:---|:---|
| 1 | Stat editing | Edit sources only (level, class, equipment, skills), not computed stats | Computed stats are derived — editing them directly would be overwritten on next recalculation |
| 2 | Class reassignment skill mapping | Universal skills keep levels; class-exclusive skills mapped by sort order (no levels lost if possible) | Preserves player investment; sort-order mapping is deterministic and fair |
| 3 | Level/XP independence | Both editable independently | Admin may need to set specific XP amounts for testing level-up behavior |
| 4 | Multi-character | One character per player (current MVP limit respected) | Multi-character is a future phase |
| 5 | Item crafting modes | Both manual (full control) and random (quick generate) | Manual for precise testing, random for quick grants |
| 6 | Item stat override | No direct stat override — stats derived from components. Change prefix/rarity to affect stats. | Keeps stat calculation consistent; prevents orphaned stat values |
| 7 | Existing item editing | All components editable (prefix, quality, lore tag, suffix, rarity) except type base and gear slot | Type base and gear slot are identity — changing them is creating a new item |
| 8 | Currency scope | Essence only in 5.1; Shards via Finance Dashboard (3.6) | Avoids duplication; shard tooling already complete |
| 9 | Essence audit trail | Dedicated `admin_essence_adjustments` table (mirrors `admin_shard_adjustments`) | Consistent pattern; queryable; separate from generic activity_events |
| 10 | Progression unlock | Forward jump backfills all prior scenes as completed + boss completions (no rewards) | Keeps map state consistent; prevents impossible progression gaps |
| 11 | Boss completion reset | Deletes `boss_completions` row, allowing first-clear rewards again | Full reset is more useful for QA than replay-without-rewards |
| 12 | Skill editing scope | `CharacterSkillLevel` (idle training) only; prerequisites enforced (highlighted for admin) | Session upgrades are temporary; prerequisite enforcement prevents broken skill trees |
| 13 | Activity timeline sources | activity_events, story sessions, achievements, anti-cheat, inventory, admin actions, tickets, purchases | Comprehensive first pass; covers all major player interactions |
| 14 | Timeline default range | 7 days with "load more" pagination | Balances performance with utility; most support cases are recent |
| 15 | UI model | Separate modal dialogs from PlayerDetail | Clean separation; modals can be large without cluttering the base page |
| 16 | Bulk operations | Single player only | Multi-player bulk ops deferred to future phase |
