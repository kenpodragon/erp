# REC 5.3: Entity Type & Classification Management

This document defines the complete requirements for the Entity Type & Classification Management system — admin tooling for managing entity types, families, visual behavior mappings derived from attack types, stat block templates, and bulk classification workflows.

**Design:** [5.3_ENTITY_CLASSIFICATION_DESIGN.md](5.3_ENTITY_CLASSIFICATION_DESIGN.md) | **Schema:** [5.3_ENTITY_CLASSIFICATION_SCHEMA.md](5.3_ENTITY_CLASSIFICATION_SCHEMA.md)

## 1. Overview & Scope

### 1.1 Purpose
Section 5.3 provides admin tooling for managing the classification systems that define what entities **are**, how they **group**, and how they should **behave visually** in the battle banner. After this phase, a game admin should be able to:

- Manage entity types as first-class lookup records (replacing the free-form `entity_type` string)
- Manage entity families as first-class lookup records with metadata (replacing the free-form `entity_family` string)
- Configure visual behavior mappings on attack types that define how entities animate in the battle banner (flying, ranged, melee, magic, or custom behaviors)
- Apply stat block templates (family base + attack type multipliers) to rapidly seed new entities
- Bulk-assign attack types, families, and entity types across multiple entities
- Audit classification coverage — identify entities missing attack types, families, or visual behavior mappings

**Platform vision:** All classification systems are fully admin-configurable. A different book series (e.g., sci-fi) could define its own entity types ("mech", "alien"), families ("Cyborg Collective"), and visual behaviors ("hovering", "burrowing") without code changes.

### 1.2 Existing Foundation
The following classification systems already exist in the database:

| System | Current State | What 5.3 Does |
|--------|--------------|----------------|
| `entity_type` field (entities) | Free-form `VARCHAR(50)` — 9 distinct values: "enemy", "creature", "character", "manifestation", "object", "group", "environment", "event", "other" | Normalize into `entity_types` lookup table with admin CRUD |
| `entity_family` field (entities) | Free-form `VARCHAR(100)` — currently **all NULL** (0 populated values). Column exists but unused. | Normalize into `entity_families` lookup table with metadata |
| `attack_types` table | 13 seeded types, many-to-many via `entity_attack_types` | Extend with `visual_behavior` mapping column for banner rendering |
| `entity_attack_types` junction | Links entities to attack types, supports `is_primary` | No structural changes — bulk assignment UI added |
| ContentEditor "Attack Types" tab | CRUD on `attack_types` table | Consolidate under WorldBuilder umbrella |
| `entity_gameplay_data.stat_block` | JSONB field — `{"strength": N, "agility": N, "intelligence": N}` | Stat block templates for rapid population |

### 1.3 Scope Boundaries
- **In Scope:** Entity type normalization, entity family normalization, visual behavior mapping on attack types, stat block templates, bulk classification assignment, classification audit view, WorldBuilder consolidation.
- **Out of Scope:** Actual PixiJS banner rendering integration (deferred — see §8). Stat balancing/economy tuning (5.5). Dev content audit dashboard (5.6). C_ generators for sprite/animation assets.
- **Dependencies:** 5.2 (Game Content Editor) complete — entity editor, attack type CRUD, and WorldBuilder page exist.

## 4. Visual Behavior Mapping (Attack Type Extension)

### 4.1 Concept
Visual behavior tags are **derived from attack types** via a mapping. Each attack type can optionally define a `visual_behavior` that controls how entities with that attack type render in the battle banner (animation set, positioning, movement pattern, attack VFX).

Since entities can have multiple attack types, the **primary attack type** determines the dominant visual behavior, with secondary types contributing supplemental effects.

### 4.2 Visual Behavior Definitions
A new `visual_behaviors` table stores admin-configurable behavior definitions.

**Requirements:**
- [x] **4.2.1** Create `visual_behaviors` table with `id`, `name` (unique system key), `display_name`, `description`, `animation_config` (JSONB — defines animation set, Y-offset, movement pattern, attack VFX config), `sort_order`, timestamps.
- [x] **4.2.2** Seed initial behaviors: `grounded_melee` (close-range swing), `grounded_ranged` (projectile from distance), `airborne` (floating/flying, elevated Y-position), `magic_caster` (spell VFX, stationary), `hybrid` (default fallback for mixed types).
- [x] **4.2.3** `animation_config` JSONB structure:
  ```json
  {
    "y_offset": -20,
    "movement_pattern": "hover",
    "attack_animation": "spell_cast",
    "attack_vfx": "magic_burst",
    "idle_animation": "float",
    "speed_modifier": 0.8
  }
  ```
  Fields are defined but **not consumed by the renderer yet** (deferred to C_ pass — see §8).

### 4.3 Attack Type → Visual Behavior Mapping
- [x] **4.3.1** Add `visual_behavior_id` (FK, nullable) column to `attack_types` table. Each attack type can optionally map to a visual behavior.
- [x] **4.3.2** Seed default mappings:
  - `melee` → `grounded_melee`
  - `ranged` → `grounded_ranged`
  - `aerial` → `airborne`
  - `akashic` → `magic_caster`
  - `psychic` → `magic_caster`
  - `void` → `magic_caster`
  - `resonance` → `grounded_ranged`
  - `nanite`, `phase`, `construct`, `thermal`, `gravitic`, `corruption` → `hybrid` (admin can remap later)
- [x] **4.3.3** Admin UI: on the attack type edit form, a dropdown to select the associated visual behavior.
- [x] **4.3.4** Entity detail view shows the **resolved visual behavior** — determined by primary attack type's mapping, with a note if secondary types have conflicting behaviors.

### 4.4 Visual Behavior Admin UI
- [x] **4.4.1** CRUD interface for visual behaviors: create, edit, delete with deletion blocking (if attack types reference it).
- [x] **4.4.2** JSON editor for `animation_config` with field descriptions.
- [x] **4.4.3** Preview panel placeholder — displays the config values in a formatted view (actual animation preview deferred).
- [x] **4.4.4** Shows which attack types map to this behavior and how many entities inherit it (transitive count).

## 5. Stat Block Templates

### 5.1 Concept
Stat block templates enable rapid entity creation by combining **family base stats** with **attack type multipliers**. Templates are **starting points** — once applied to an entity, the entity's stat block is independent (no ongoing link to the template).

### 5.2 Family Stat Templates
- [x] **5.2.1** Add `base_stat_template` (JSONB, nullable) column to `entity_families` table.
  ```json
  {
    "strength": 10,
    "agility": 20,
    "intelligence": 15,
    "base_hp": 100,
    "base_gold": 10
  }
  ```
- [x] **5.2.2** Admin UI: editable stat template on the entity family edit form with labeled number inputs per stat.
- [x] **5.2.3** Template values are **base values** before attack type multipliers are applied.

### 5.3 Attack Type Stat Multipliers
- [x] **5.3.1** Add `stat_multipliers` (JSONB, nullable) column to `attack_types` table.
  ```json
  {
    "strength": 1.5,
    "agility": 0.8,
    "intelligence": 1.0,
    "hp_multiplier": 1.2,
    "gold_multiplier": 1.1
  }
  ```
- [x] **5.3.2** Admin UI: editable multiplier fields on the attack type edit form.
- [x] **5.3.3** When multiple attack types are assigned, multipliers from the **primary** attack type are used.

### 5.4 Template Application Workflow
- [x] **5.4.1** "Apply Template" button on entity gameplay data panel (EntityGameplayPanel in 5.2).
- [x] **5.4.2** When clicked:
  1. Reads the entity's family → gets `base_stat_template`.
  2. Reads the entity's primary attack type → gets `stat_multipliers`.
  3. Computes final stats: `base_value × multiplier` per stat field.
  4. Shows a **preview** of the computed stat block alongside the current stat block.
  5. Admin confirms → stat block is written to `entity_gameplay_data.stat_block`, `base_hp`, and `base_gold`.
- [x] **5.4.3** If entity has no family or no primary attack type, show a warning and allow partial application (family-only or multiplier-only).
- [x] **5.4.4** "Bulk Apply Templates" action on the classification audit view (§7) — apply templates to all entities in a filtered set that currently have empty/null stat blocks.

## 9. Deferred: Banner Rendering Integration

### 9.1 What's Deferred
The actual PixiJS rendering changes that consume visual behavior configurations are **not part of 5.3**. Specifically:
- Modifying `CombatStage.tsx` to read `visual_behavior` data and adjust entity rendering (Y-offset, animation, movement pattern).
- Modifying `BottomAnimatedBanner.tsx` (hub banner) to reflect entity classifications.
- Creating actual animation sprite sheets or PixiJS animation sequences per behavior.

### 9.2 C_ Requirement
A new C_ requirement should be created: **"C_BANNER_ANIMATION_SYSTEM"** covering:
- Consuming `visual_behaviors.animation_config` in the PixiJS renderer.
- Per-behavior animation state machines (idle, attack, move, death).
- Asset generation for animation sprite sheets per visual behavior.
- Integration with the Asset Registry (5.7) for animation asset storage.

This ensures 5.3 builds the **data foundation** and 5.4 + C_ build the **visual implementation**.

## 11. Design Decisions (Resolved)

| # | Decision | Resolution | Rationale |
|---|----------|------------|-----------|
| Q1 | Entity type taxonomy | Normalize into `entity_types` lookup table | Enables admin CRUD, consistent with platform reusability vision |
| Q2 | Entity family scope | Normalize into `entity_families` lookup table with metadata | First-class records with icon, description, lore reference; enables stat templates |
| Q3 | Visual classification tags | Derived from attack types via `visual_behavior_id` mapping | Avoids redundant tagging; attack types already classify combat style |
| Q4 | Banner behavior implementation | Data model + admin UI now; rendering deferred to C_ | PixiJS changes are non-trivial; data foundation first |
| Q5 | Stat block templates | Family base + attack type multipliers; starting points (copy, then independent) | Balances rapid creation with per-entity customization |
| Q6 | Bulk assignment scope | All classification types + classification audit view | Comprehensive coverage for 3,936+ entities |
| Q7 | ContentEditor integration | Consolidate under WorldBuilder umbrella | Single entry point for all content management |
| Q8 | Platform reusability | Fully generic — admin-configurable visual behaviors | Different book series can define their own behaviors without code changes |
